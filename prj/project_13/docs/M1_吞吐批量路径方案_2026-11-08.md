# 0. 一页速览

| 问题 | 结论 |
|---|---|
| 现在多快 | **≈23 Mbps**（软核逐帧 DMA，路线 B），单帧开销 **≈390 µs** |
| 硬件路线能做到多快 | **≈969 Mbps**（路线 A 实测报告，1466 B 帧），单帧 ≈12.1 µs |
| 差距是什么 | **不是带宽，是每帧的固定开销**：390 µs / 12.1 µs = **32×**；而一帧 1500 B 的 DDR 突发只要 **0.08 µs** |
| DDR 会不会是瓶颈 | **不会**。AXI 峰值 19.2 GB/s，969 Mbps 只占 **0.6%**；10 Gbps 全双工也只占 13% |
| AXI 主机数会不会变 | **不会**。两条路线都复用现有 S00 口，不动 `axi_arb_3to1` |
| 该选哪条 | **先测「每批固定开销 vs 每帧边际开销」的斜率**，再决定：固定开销为主 → 路线 1（描述符队列）；边际开销为主 → 路线 2（硬件 FSM） |
| 本轮为什么不做 | 无板（测不出斜率）+ B1 未上板验证 + P2 RTL 在改 + 改的就是 B1 刚修的那条通路 ⇒ 叠加未知量 |
| 资源代价量级 | 路线 1：+1~2 BRAM、+0.6~1.2 k LUT、0 DSP；路线 2：可能 **LUT 净减少**（退掉 axi_dma 写通道） |

# 1. 现状与数字来源（先分清「实测 / 推导 / 假说」）

## 1.1 三个原始数字

| 数字 | 值 | 来源 | 性质 |
|---|---|---|---|
| 路线 B 连续吞吐 | **≈23 Mbps** | 指南 §6.1（`GSnFPipe_A组_…_v1.0.md:243`）+ §1 成果表 `:52` | 学生历史报告实测 |
| 路线 B 单帧开销 | **≈390 µs/帧** | 开工手册/任务书给定（观测值） | 实测（P1 探针节奏反推） |
| 路线 A 纯硬件吞吐 | **≈969 Mbps @1466 B 帧** | 指南 `:51` 与 `:243` | 历史报告实测 |

## 1.2 三个数字互相校验（这一步必须做，否则会算出互相矛盾的结论）

```
路线 B：390 µs/帧  -> 2,564 帧/s
        23 Mbps = 2.875 MB/s -> 2,875,000 / 2,564 = 1,121 B/帧
        => 23 Mbps 与 390 µs/帧 在「约 1.1 KB 载荷」下自洽
路线 A：969 Mbps = 121.1 MB/s，1466 B/帧 -> 82,626 帧/s -> 12.1 µs/帧
比值  ：390 / 12.1 = 32.2x
DDR  ：1500 B / (64 B/beat @300 MHz) = 24 beat = 80 ns = 0.08 µs/帧
       即 12.1 µs 里只有 0.7% 是真正的 DDR 传输时间
```

**结论**：`23 Mbps` 和 `390 µs/帧` 不是矛盾，而是同一件事的两面（约 1.1 KB 帧）。
但要注意：**吞吐随帧长线性变化**，因为开销是「每帧」而不是「每字节」。
用 1466 B 帧、同样 390 µs/帧，理论上是 30 Mbps —— 也就是说「23 Mbps」里已经有一部分是帧长偏小造成的。
这直接影响优化目标：**先加大帧长，再谈架构**。

## 1.3 一帧的时间预算（当前路线 B，单位 µs）

| 环节 | 估计 | 依据 |
|---|---|---|
| 以太网收帧 → 泵 → `frame_mem_if`（user_clk 100 MHz） | 0.1–1 | 154 B 帧在 user_clk 上约 1.5 µs 的字节流，流水化后摊销 |
| async FIFO 跨域（gray 指针 2FF） | ~0.02 | 2–3 个 ui_clk |
| 写引擎拿描述符 → S2MM 流（3 beat） | 0.1 | 3 × 5 ns + WAITGO |
| **软核服务一次**（中断/轮询 + C 代码 + 翻 GO + 完成中断） | **~380** | 390 µs 减去上面所有项后的余额 |
| 读回程（pack → Aurora） | 0.1–1 | 对称 |

> 380 µs 什么概念：MicroBlaze @100 MHz 上约等于 38,000 条指令。真实固件不会每帧跑 38k 条指令，
> 更可能是**轮询粒度**（`main.c` 的 serve 循环 + 中断/定时器节拍）主导。
> **这是假说，必须用 §4.1 的斜率实验证伪** —— 如果是轮询粒度，那么「描述符队列」的收益会比估算更大
> （一次 GO 服务 N 帧，轮询粒度被摊薄 N 倍）。

# 2. 两条候选路线的 RTL 结构

## 2.1 共同现状（改之前长什么样）

```
eth → pump → frame_mem_if(user_clk) ──[u_wr_bytes / u_wr_desc FIFO]──> axi4_master_bridge(ui_clk)
                                                                          │
                             HAS_DMA=1 (桥①/u_mem)                        │
                             ├─ g_wr_dma : 每帧一次请求 → 软核翻 GO →    │
                             │             S2MM 流 → axi_dma → S00 ──────┤
                             HAS_DMA=0 (桥②/u_mem2)                       │
                             └─ g_wr_hw  : 硬件写 FSM (W_IDLE…W_PUSH) → S01
                                                                          ▼
                                                       axi_arb_3to1 → MIG 单从机口 → DDR4
```

关键事实（已核对源码）：

- 写路径的引擎是**结构常量分派**：`axi4_master_bridge.v:372` `generate if (!HAS_DMA)` 装硬件写 FSM；
  `:564` 起是 HAS_DMA=1 的 S2MM 写引擎。**桥②的硬件 FSM 已经在板上跑着**（B→A 回程），
  也就是说「硬件 FSM 写 DDR」这条路**不是新写的，是已经验证过的代码**。
- AXI 主机数：`axi_arb_3to1`（`aurora_mem_bridge.v:1067`），S00 = axi_dma S2MM（桥①写），
  S01 = 桥②（读+写），S02 = axi_dma MM2S（读）。**MIG 只有一个从机口**（`:1064` 注释）。
- 每帧握手：软核服务 ↔ `ro_dma_wr_req[31]`（pending）↔ `dma_wr_go` 翻转 ↔ `s2mm_introut` 完成中断。

## 2.2 路线 1：描述符队列（SG-DMA / 批量提交）

### RTL 结构

```
frame_mem_if                                 axi4_master_bridge (HAS_DMA=1, 改)
  u_wr_desc (8 深, 16b len)                    ┌──────────────────────────────┐
        │                                      │ dq_ram: 256 x {slot,len,flags}│  ← 新增 1 块 BRAM
        ▼                                      │  (2 KB, 1 RAMB18 或半个 36)   │
  [新增] desc_batch_collector ────────────────>│ dq_wr / dq_rd 指针(各 1 个)   │
   · 攒够 N 帧或超时 T 再提交                   │ dq_level / dq_ovf 计数         │
   · 只在这一层碰软核边界                       │                              │
                                               │ 现有 g_wr_dma 引擎 **逐帧**   │
   软核侧：一次 GO = 一批 N 帧                 │ 从 dq 取 {slot,len} 驱动 S2MM │
   完成中断：每批一次                          │ (stream 通路完全不改)         │
                                               └──────────────────────────────┘
```

**核心思想**：不动 512-bit 流和 S2MM 引擎，只在**软核 ↔ 引擎**之间插一层队列，
把「每帧一次软核往返」变成「每 N 帧一次」。

| 改动面 | 估计 |
|---|---|
| 新增 `desc_queue.v`（或并入 `axi4_master_bridge`） | ~250–400 行 |
| `g_wr_dma` FSM：`W_IDLE` 从 dq 取描述符（而非从 `wd_empty`） | 改 ~20 行 |
| 软核侧 `main.c`：一次 GO 服务 N 帧 + 批量完成中断 | C 侧改动 |
| 新增寄存器（dq_level/dq_ovf/dq_batch/batch_done 计数） | `axi_lite_regs.v` +6~10 行 |

## 2.3 路线 2：硬件 FSM 直接写（软核退出数据面）

### RTL 结构

```
frame_mem_if                          axi4_master_bridge (HAS_DMA=1 → 改造成「无 DMA」)
  u_wr_desc (8 深)                      ┌───────────────────────────────────────────┐
        │                               │ dq_ram (同路线 1)                         │
        └──────────────────────────────>│ g_wr_hw FSM（**现成**，桥② 已在板上验证）│
                                        │  W_IDLE→W_WAIT→W_AW→W_FILL→W_PUSH→提交     │
                                        │  512-bit 组装 + wstrb + wlast（不改）      │
                                        │  commit queue (CQ, 4 深) + slot 表（不改） │
                                        └───────────────────────────────────────────┘
                                                 │
                                                 ▼ 直接接 S00（原 axi_dma S2MM 位置）
                                            axi_arb_3to1 → MIG
```

**核心思想**：把「已经存在的硬件写 FSM」从桥②搬到桥①，删除 `axi_dma` 在写路径上的角色。
软核只做「开机初始化 + 配置 + 状态查询」，完全不进逐帧关键路径。

| 改动面 | 估计 |
|---|---|
| `HAS_DMA` 语义从「二选一」变成「桥①也用硬件 FSM」 | 参数重排 + 顶层接线 ~30 行 |
| 描述符队列（同路线 1） | 复用 |
| 退掉 `axi_dma` 的写通道（S2MM）→ S00 改接 `g_wr_hw` | `aurora_mem_bridge.v` ~40 行 + BD 里改 1 个连接 |
| 删除 `dma_wr_go/ack/introut` 协议（保留为调试） | `frame_mem_if.v` 端口保留、接线断开 |
| 软核侧：删掉逐帧服务循环 | C 侧净减少 |

**为什么这条路线风险反而低**：`g_wr_hw` 不是新代码 —— 它就是桥②（B→A 回程）在板上跑了几百帧的那套
FSM（`axi4_master_bridge.v:372-560`），包括 4KB 规则、`w_bad_len`、`W_DRAIN`、CQ 保序提交。
新写的只有「从 dq 取描述符」这一层。

## 2.4 两条路线怎么选（先测斜率，不要先选架构）

设每批固定开销 `C`（软核一次往返）、每帧边际开销 `m`（硬件流水 + 描述符）：

```
吞吐(帧/s) = N / (C + N·m)      N = 每批帧数
N → ∞ 时 吞吐 → 1/m
```

- 若 `C ≈ 380 µs` 且 `m ≈ 12 µs`：`N=16` → 36.4 µs/帧（27.5 k 帧/s，1466 B 下 **322 Mbps**），
  `N=32` → 24.7 µs/帧（**475 Mbps**），渐近 969 Mbps。
  ⇒ **只加队列就能拿一个数量级**，但天花板还是被 `m` 卡住。
- 若 `C ≈ 100 µs`、其余是「每帧中断 + C 代码」（即 `m ≈ 290 µs`）：队列收益极小，
  必须走路线 2（把 `m` 也压到硬件级）。
- 若 `C ≈ 380 µs` 里大头是**轮询节拍**（而非常量指令数），则 `C` 会被队列摊薄得很好 → 路线 1 优先。

**这个分解必须实测**（§4.1），不能从 23 Mbps 反推 —— 这是本方案唯一真正的未知量。

# 3. 资源与时序影响评估

## 3.1 当前基线（实测，prj12 2026-10-24 构建）

| 资源 | 用量 | 占比 |
|---|---|---|
| CLB LUTs | 43,104 | 13.00% |
| CLB Registers | 60,255 | 9.08% |
| Block RAM Tile | 87.5 | 8.10% |
| DSPs | 3 | 0.11% |
| MMCM | 2 | 16.67% |

时序：`WNS +0.032 / WHS +0.004`（B1 构建后 `+0.029 / +0.004`，0 失败端点）。
**WHS 只有 4 ps 余量**是本次评估的第一约束 —— 任何在复位/使能/握手路径上加逻辑的改动都可能打穿它。

## 3.2 资源增量估计

| 项 | 路线 1（描述符队列） | 路线 2（硬件 FSM 写） |
|---|---|---|
| BRAM | +1~2 RAMB18/36（256×64b 队列 ≈2 KB） | +1~2（同队列），**但可能 −N**（退掉 axi_dma 内部缓冲） |
| LUT | +600~1,200 | +600（队列）**− 2,000~5,000**（axi_dma 写通道退出） |
| FF | +800~1,500 | 同上，净可能为负 |
| DSP | 0 | 0 |
| 关键路径 | 队列读写都在 ui_clk 300 MHz；**不动 512-bit 流** | 同左，但 S00 的 AW/W 驱动源从 axi_dma 改成本地 FSM（桥②已验证同样的路径） |
| WNS 风险 | **低**（新逻辑不在数据通路上） | **低**（复用桥②已验证的 FSM） |
| WHS/removal 风险 | **中**：队列的 `empty→valid` 可能插进 tready/tvalid 的复位锥 | **中低**：`g_wr_hw` 的复位用法与桥②一致，扇出更小 |
| 是否需要重构建 | **是**（全综合+实现 70–80 min） | **是**（另加 BD 改动） |

**红线**（沿用 `build_impl.tcl` 守门 + FIX_PLAN B1.4 回退链）：WNS<0 或 WHS<0 → 拒绝写位流；
禁止「为了过时序去关 ILA / 放松时钟约束」。

## 3.3 DDR 带宽与 AXI 主机数

| 项 | 数值 | 说明 |
|---|---|---|
| AXI 峰值（ui_clk 300 MHz × 512 bit） | **19.2 GB/s**（153.6 Gb/s） | `aurora_mem_bridge.v:241` 注释 ui_clk ~300 MHz |
| MIG DDR4 理论 | 19.2 GB/s（64-bit @2400 MT/s） | 实际可达通常 70–85% → 13–16 GB/s |
| 969 Mbps 需 DDR | 121 MB/s（单向） | = **0.6%** 峰值 |
| 10 Gbps 全双工需 DDR | 2.5 GB/s（双向合计） | = **13%** 峰值 |
| 一帧 1500 B 的 DDR 时间 | 24 beat × 3.33 ns = **80 ns** | 与 390 µs 差 4,875 倍 |

⇒ **DDR 完全不是瓶颈**，两条路线都不需要动 MIG 配置、不需要加 DDR 端口。

**AXI 主机数**：现状 3 个（S00/S01/S02）共用 MIG 唯一从机口。两条路线：

- 路线 1：S00 的驱动者仍是 axi_dma，**主机数不变**；
- 路线 2：S00 的驱动者换成 `g_wr_hw`，**主机数仍不变**（只是换驱动源）。

⇒ `axi_arb_3to1` 不用改、不用加端口。唯一要注意的是**公平性**：
如果新的写路径长时间霸占仲裁，桥②（B→A 回程）和 MM2S 的读延迟会上升。
判别方法：长跑时盯 `mem2_ost`（桥② 未完成槽数）与 `mem_wr_stall`；
若 `mem2_ost` 持续 > 8 或 `mem_stall` 开始增长，说明仲裁饥饿，需要在写路径上加「连续 N 帧后让出」的节流。

# 4. 切换时机判断

## 4.1 切换前**必须**先做的三件事

| # | 实验 | 为什么必须先做 | 判据 |
|---|---|---|---|
| 1 | **代价结构斜率实验**：固定帧长 1466 B，分别以「1 / 4 / 16 / 64 帧一次 GO」发送，测 fps | 决定 `C` 与 `m` 的分解，直接决定选路线 1 还是 2；也验证「23 Mbps 里有多少是轮询粒度造成的」 | 拟合 `t(N) = C + N·m`，给出 `C`、`m` 与 R² |
| 2 | **现状上限**：10 MiB 单向（1472 B × 7125 帧，0 丢/0 重/`fill` 全 ok），记吞吐与耗时 | 这是 P0-3/P0-4 的交付，也是「要不要切」的基线数字 | 吞吐 ≥ 23 Mbps（再现）；给出帧率与 CPU 侧发送能力上限 |
| 3 | **P2 转发上限**：P2 位流上同样跑 10 MiB | 不先有 P2 的转发路径，谈吞吐没有意义（当前在跑的是回显语义） | V4（#10 契约）通过 |

## 4.2 触发条件（满足任一即应排期切换）

| 触发 | 阈值 | 依据 |
|---|---|---|
| **业务需求缺口** | 协议 v0.2 要求的持续速率 > 实测上限的 50% | 需要 B 组给出 PP 训练的带宽需求（issue #6/#10 未冻结）→ **当前未知** |
| 单帧开销过高 | `m` 或 `C+N·m` > 100 µs/帧（即 < 100 Mbps @1466 B） | 23 Mbps 已远超（390 µs） |
| 软核占空比过高 | 长跑期间软核无法响应 `U` 命令 / `stat_wr_timeout` 增长 | 说明数据面挤压了控制面 |
| 长跑稳定性 | M2 长跑中出现 `stat_wr_timeout>0` 或恢复看护频繁触发 | 与 P1-6 的看护日志联动判读 |

## 4.3 **不应该**切换的时机（同样重要）

- B1 未在板上验证通过（V1/V2/V3）→ 见 §5；
- P2 转发未通过 V4 → 优化的是错的东西；
- 距离 M2 联调 < 1 周 → 新写路径需要重新标定整套判据（ILA 探针含义、`wdbg` 语义、恢复阶梯），
  这些「工程税」在联调前一周付不起；
- 没有重建位流的 2 小时窗口（综合 25–35 min + 实现 40 min + 两板重烧 + 全量回归）。

# 5. 本轮为什么不实现（明确的理由 + 前置条件）

| # | 原因 | 具体到文件/事实 |
|---|---|---|
| 1 | **无板** | 板子离线；§4.1 的三个实验一个都跑不了，`C`/`m` 分解只能猜。没有这个数字就选不了路线，写 RTL 等于赌 |
| 2 | **B1 未上板** | B1 只在 xsim 上验证过（`AUDIT §4`、`FIX_PLAN B1.2`），板上 V1/V2/V3 全部待做。而两条路线改的**正是 B1 刚修的那条写通路**（`frame_mem_if` 的 5 个 async_fifo + 写引擎）⇒ 一旦出问题，分不清是 B1 没修好、还是新引擎引入了新问题 |
| 3 | **P2 RTL 在改** | 本轮 `rtl/p2/**` 正在被并行开发（`ipv4_packet_extract.v` / `eth_rewrap.v` 等）。同一份 `axi4_master_bridge` 上叠两个未收敛的改动 = 不可归因 |
| 4 | **回归基线会被打掉** | P1-5 的 `sim/regress.ps1` 的 DUT/负对照是按**当前**写引擎结构建的（`g_wr_dma` 的 S2MM 握手、`dma_wr_t*` 采样）。换引擎后这套 TB 与 12 个 case 必须重新推导，否则「回归通过」不再有意义 |
| 5 | **改动面跨 BD** | 路线 2 要动 `mb_ctrl` Block Design 里 `axi_dma` 与仲裁器的连接（`create_bd_b.tcl` / `create_project.tcl`），这不是纯 RTL 改动，需要独立的构建验证轮 |
| 6 | **收益还没被证明需要** | 协议 v0.2 未冻结（issue #6/#10），B 组的带宽需求未知。「23 Mbps 不够」目前只是**推测**，不是需求 |

## 前置条件（按顺序，全绿才开工）

1. B1 位流上板 V1/V2/V3 通过（含「5 次闪断后 `pk+3`」）；

# 6. 实施顺序建议（等前置条件全绿）

| 阶段 | 内容 | 产出 | 预计 |
|---|---|---|---|
| S1 | 描述符队列 + 现有 S2MM 引擎（路线 1 最小版） | `desc_queue.v` + 批量 GO 的固件 + dq 计数寄存器 | RTL 2–3 天；构建 75 min |

| S4 | （若 S2 显示 `m` 仍是瓶颈）路线 2：`g_wr_hw` 上桥① | BD 改动 + 顶层重排 | RTL 2 天；构建 75 min |

**验收门槛**（写死，避免「差不多就行」）：
- 10 MiB 单向：0 丢 / 0 重 / `fill` 全 ok，吞吐 **≥ 300 Mbps**（路线 1、N=16 的目标值）或 **≥ 800 Mbps**（路线 2）；
- 双向 20 帧仍 20/20；
- 10 min 稳定不掉链、`mem2_ost` 不增长、`stat_wr_timeout=0`；
- WNS≥0 且 WHS≥0（`build_impl.tcl` 守门）；
- P1-5 回归矩阵全绿（含 `silent` / `multi` / `mem2` 三支）。

# 7. 未验证点（诚实边界）

1. `23 Mbps` / `969 Mbps` / `390 µs` 三个数字来自**历史报告与观测**，本轮**没有复测**（无板）。
2. `C ≈ 380 µs` 的分解是**推导**，不是实测；§4.1 的斜率实验是本方案唯一的关键未知量。
3. 压缩率、DDR 实际可达带宽（70–85%）均为**行业经验值**，未在本板测量。
4. 资源增量（LUT/BRAM/FF）是**量级估计**，必须由综合报告确认。
5. 「路线 2 可能 LUT 净减少」依赖 `axi_dma` 写通道能被完全裁掉 —— 若 BD 里该 IP 与读通道共用，则只能裁一半。
6. 仲裁公平性影响（`mem2_ost` 升高）是**预测**，需长跑观测。
