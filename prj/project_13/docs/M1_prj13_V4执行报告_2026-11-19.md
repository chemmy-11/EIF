### 1.4 角色映射裁决（重要，避免混淆）

prj13 的 `pc/static_arp.ps1` 与 RTL 参数组都假设「PC1↔板 A / PC2↔板 B」，但**本窗口物理接线是 PC1↔物理板 B、PC2↔物理板 A**。
裁决：**A/B 是软角色** —— 软角色 A 部署到 PC1 侧那块板、软角色 B 部署到 PC2 侧那块板（两板同型号同器件，可互换；零 RTL 改动）。

## 3. T5 两向 3 帧门：通路成立、字节级 FAIL

### 3.1 通路（两侧 ILA 计数）

| | A 侧（发送） | B 侧（接收） |
|---|---|---|
| 发送计数 | `pfwd_wr 0→12`、`pk_frames 0→12`（4 轮 ×3 帧全部上 Aurora） | — |
| 接收计数 | `up_frames 0→3`、`prev_wr 0→3` | `up_frames 0→12`、`prev_wr 0→12`、`mem2_wr/rd_frm 0→12`、`mem_u_drop=0` |

⇒ **板间 Aurora 通路双向成立**，链路 `ch_up/lane_up/pll=1`、`aurora_rst=0`、`hard/soft=0`。

### 3.2 pcap 字节级（FAIL）

- PC2 侧 180 s 窗（20:22:07.6–20:25:07.6，`v4_t5_a2b_final.pcap`，55 帧）：
  `src_mac_histogram = {a8:2b:dd:76:df:a2: 55}` —— **全部是 PC2 自己的流量**，没有一帧来自板 MAC。
- 其中 20:24:02–20:24:22（含 A 侧 20:24:12.211 发出的 3 帧）共 35 帧，全为 PC2 自身 mDNS/IGMP/LLMNR。
- 无过滤审计：`frames 55 / ip 39 / arp 0 / len_ok 39 / len_bad 0`（审计工具本身正常，判据在真数据上可运行）。

### 3.3 关键对照（定位到设计侧出口）

PC2 在 20:26:30 抓 8 s + 同时 `ping 10.10.0.12` ×3（`ping_probe.pcap`，11 帧）：

| 帧 | src → dst | 说明 |
|---|---|---|
| #1/#2/#4/#5/#7/#8 | `a8:2b:… → 02:00:00:00:0b:01` | PC2 的请求 |
| **#3/#6/#9** | **`02:00:00:00:0b:01 → ff:ff:ff:ff:ff:ff`** | **板的 ICMP 应答（被成功抓到）** |

⇒ **同一条 RGMII TX：板本地栈的帧能上 PC2 的网线；而 Aurora→pump B 的转发帧（`prev_wr` 已 +6）一帧都没出。**
⇒ 网卡侧排除：`ReceivedPacketErrors=0`、`ReceivedDiscardedPackets=0`，且能抓到板卡广播应答。

**判定：T5 = 通路成立 / pcap 字节级 `FAIL`（设计侧出口待查：pump B 写入但未上线）。**

## 4. 两条设计发现（单独立项）

### D1：pump B 写入但未上线路（阻断 V4）

- 现象见 §3.3。转发帧在 B 侧 `prev_wr`/`mem2_*` 计数增长，但不出现于 PC2 网线。
- 影响：**prj13 P2 的 Aurora→PC 出口不通**，V4 全部功能项无法闭环。
- 待查：pump B 读出使能、RGMII TX 仲裁、`prev_wr` 之后的读路径（当前 ILA 探针都在进向，**没有 pump B 读出侧探针**，需加探针重建，约 38 分钟一轮）。

### D2：P2 契约非一致性 —— 发射帧 dst MAC 是广播

- 实测：板卡 ICMP 应答 `dst = ff:ff:ff:ff:ff:ff`。
- 契约（`pc/README.md` §4）：P2 口径要求 **单播 = 本端 PC MAC**，`--no-bcast` 硬判。
- 后果：`twin_recv --no-bcast` 对任何板卡帧必然 0 匹配。
- 处置：本窗口**未改判据、未改设计**，仅记录；广播口径单独落账。

## 5. 吞吐基线（A 侧单板，`out/evidence_20261119_p13_v4/log/TPUT_BASELINE_A.md`）

方法：`twin_send.py` **内部计时**（排除进程启动开销），串口计数差分。

| len | 主机速率 | 板上收下 | 收下率 | 板上线上速率 |
|---|---|---|---|---|
| 1472 | 1745 fps（0.2 ms） | 1500/1500 | **100%** | **21.13 Mbps** |
| 1472 | 69,420 fps（0 ms 突发 / 817.5 Mbps） | 57/1500 | 3.8% | 31.96 Mbps |
| 100 | 1753 fps（0.2 ms） | 2000/2000 | **100%** | 1.99 Mbps |
| 100 | 119,558 fps（0 ms 突发 / 95.6 Mbps） | 51/2000 | 2.6% | 3.47 Mbps |

- **⚠ 结论限定**：两种帧长的主机极限都卡在 ≈1745 fps ⇒ **瓶颈在主机侧 Python 发送器**，不是板子。
  **桥的吞吐上界 = `NOT_TESTED`**（未用 C / 原生 raw socket 发送器测过）。
- 0 ms 突发时板上大量丢弃（96–97%），说明突发吸收能力有限；**未定位是 FIFO 深度还是服务速率**。
