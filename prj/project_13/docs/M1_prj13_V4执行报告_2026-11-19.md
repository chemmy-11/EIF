## 3. T5 两向 3 帧门：通路成立、字节级 FAIL

### 3.1 通路（两侧 ILA 计数）

| | A 侧（发送） | B 侧（接收） |
|---|---|---|
| 发送计数 | `pfwd_wr 0→12`、`pk_frames 0→12`（4 轮 ×3 帧全部上 Aurora） | — |
| 接收计数 | `up_frames 0→3`、`prev_wr 0→3` | `up_frames 0→12`、`prev_wr 0→12`、`mem2_wr/rd_frm 0→12`、`mem_u_drop=0` |

⇒ **板间 Aurora 通路双向成立**，链路 `ch_up/lane_up/pll=1`、`aurora_rst=0`、`hard/soft=0`。

### 3.2 pcap 字节级（FAIL）

- PC2 侧 180 s 窗（20:22:07.6–20:25:07.6，`v4_t5_a2b_final.pcap`，55 帧）：
  `src_mac_histogram = {a8:2b:dd:76:df:a2: 55}` —— **全部是 PC2 自己的流量**，没有一帧来自板 MAC。
- 其中 20:24:02–20:24:22（含 A 侧 20:24:12.211 发出的 3 帧）共 35 帧，全为 PC2 自身 mDNS/IGMP/LLMNR。
- 无过滤审计：`frames 55 / ip 39 / arp 0 / len_ok 39 / len_bad 0`（审计工具本身正常，判据在真数据上可运行）。

### 3.3 关键对照（定位到设计侧出口）

PC2 在 20:26:30 抓 8 s + 同时 `ping 10.10.0.12` ×3（`ping_probe.pcap`，11 帧）：

| 帧 | src → dst | 说明 |
|---|---|---|
| #1/#2/#4/#5/#7/#8 | `a8:2b:… → 02:00:00:00:0b:01` | PC2 的请求 |
| **#3/#6/#9** | **`02:00:00:00:0b:01 → ff:ff:ff:ff:ff:ff`** | **板的 ICMP 应答（被成功抓到）** |

⇒ **同一条 RGMII TX：板本地栈的帧能上 PC2 的网线；而 Aurora→pump B 的转发帧（`prev_wr` 已 +6）一帧都没出。**
⇒ 网卡侧排除：`ReceivedPacketErrors=0`、`ReceivedDiscardedPackets=0`，且能抓到板卡广播应答。

**判定：T5 = 通路成立 / pcap 字节级 `FAIL`（设计侧出口待查：pump B 写入但未上线）。**

## 4. 两条设计发现（单独立项）

### D1：pump B 写入但未上线路（阻断 V4）

- 现象见 §3.3。转发帧在 B 侧 `prev_wr`/`mem2_*` 计数增长，但不出现于 PC2 网线。
- 影响：**prj13 P2 的 Aurora→PC 出口不通**，V4 全部功能项无法闭环。
- 待查：pump B 读出使能、RGMII TX 仲裁、`prev_wr` 之后的读路径（当前 ILA 探针都在进向，**没有 pump B 读出侧探针**，需加探针重建，约 38 分钟一轮）。

### D2：P2 契约非一致性 —— 发射帧 dst MAC 是广播

- 实测：板卡 ICMP 应答 `dst = ff:ff:ff:ff:ff:ff`。
- 契约（`pc/README.md` §4）：P2 口径要求 **单播 = 本端 PC MAC**，`--no-bcast` 硬判。
- 后果：`twin_recv --no-bcast` 对任何板卡帧必然 0 匹配。
- 处置：本窗口**未改判据、未改设计**，仅记录；广播口径单独落账。

## 10. 追加（2026-11-19 20:5x）：D1 根因排查 + iperf 应用级佐证 + ILA7 重建

### 10.1 D1 排查：定位到 RGMII TX 三路 mux

tl/aurora_mem_bridge.v:1427-1430：

```verilog
assign rgmii_txd_o   = cmd_takeover   ? cmd_resp_txd   :
                       stack_takeover ? stack_txd      : rgmii_txd_i;   // ← 转发帧（pump_rev）
assign rgmii_tx_en_o = cmd_takeover   ? cmd_resp_tx_en :
                       stack_takeover ? stack_tx_en    : rgmii_tx_en_i;
```

优先级 cmd > stack > relay。**若 stack_takeover 卡在 1，转发帧永远到不了引脚**，
而栈自身的 ARP/ICMP 仍能正常发出 —— 与 §3.3 观测（ICMP 应答能出、转发帧不出）完全吻合。

其锁存逻辑（:1412-1423）：

```verilog
if (~stack_tx_en & stack_tx_en_d)      stack_takeover <= 1'b0;   // 只有下降沿才释放
else if (stack_tx_en & ~stack_tx_en_d & cmd_tx_idle & ~cmd_takeover)
                                        stack_takeover <= 1'b1;
```

释放只依赖 stack_tx_en 的下降沿 —— **单点脆弱**，是本轮首要排查对象。

### 10.2 观测探针的时钟选择（依官方文档）

AMD UG908《Debug Core Clocks》：debug 核时钟必须**自由运行且稳定**，并**与被测信号同域同步**，
否则会得到损坏数据或 "Debug Cores not detected"。
（https://docs.amd.com/r/en-US/ug908-vivado-programming-debugging/Debug-Core-Clocks）

上述信号全部在 `posedge gmii_rx_clk` 域，故新增 ILA 核 u_ila_7 挂 gmii_rx_clk
（RGMII RX 时钟；链路 up 时自由运行）。

### 11.2 **D1 假设被实测推翻**（本轮最重要的负结果）

原假设："RGMII TX 三路 mux 的 stack_takeover 锁存卡死，转发帧永远到不了引脚"。

PC2 用 B3 位流的 u_ila_7 触发抓取（触发 dbg_pump_rev_en eq1'b1，窗口 1024 样本，触发点 sample 512）实测：

| 探针 | 实测 | 结论 |
|---|---|---|
| dbg_stack_takeover | **0 × 1024（整窗恒 0）** | **锁存没有卡死 ⇒ 原假设不成立** |
| dbg_cmd_takeover | 0 × 1024 | 命令接管也未卡 |
| dbg_stack_txen | 0 × 1024 | 栈未占用 |
| **dbg_pump_rev_en** | **1（样本 512→653，连高约 142 拍）** | **泵 B 确实读出并驱动了 GMII TX 使能** |

- 142 拍 ≈ 0.94 µs ≈ 142 字节 ≈ 一帧长度。
- 由于 	akeover 全 0，gmii_tx_en_o = pump_rev_en ⇒ **末级 TX 使能确实拉起了**。

⇒ **问题不在 mux、不在锁存，而在更下游**（pump_rev_data 与 pump_rev_en 的数据/相位对齐、或 RGMII TX 在"泵驱动"路径上的时钟域处理）。
栈驱动路径（ICMP 应答）能出、泵驱动路径不能出，是锁定下游的关键对照。

### 11.3 新发现：prj13 P2 前向通路**在链路断-恢复后不自愈**

实测链条（全部有 ILA/串口证据）：

| 时刻 | 操作 | A 侧状态 |
|---|---|---|
| 20:24 | 正常运行 | pfwd_wr=12 / pk_frames=12 ✅ |
| 22:53 | PC2 重烧 B3 → 链路闪断 | pfwd_wr=3 / pk_frames=0、串口 wr=3 rd=0 ❌ |
| 23:08 | 重烧 A（链路已恢复） | pfwd_wr=3 / pk_frames=3 ✅ 恢复 |
| 23:12 | **光纤断开**下重烧 A，再插回 | ch_up=1 / aurora_rst=0 但 pfwd_wr=3 / **pk_frames=0** ❌ |

⇒ **一次 link-down→up 周期即足以让前向泵永久停摆（pk_frames 不再增长），只有整板重配置能恢复。**
⇒ 这比 prj12 更严重：prj12 的**空闲闪断不会死锁**（2026-11-19 A0 实证），prj13 P2 **连空闲闪断都会卡死**。
⇒ 并且**任一侧重烧都会让对侧闪断 → 对侧卡死**，形成"互相拖死"循环；本次通过"拔光纤 → 双侧重烧 → 插回"规避，但**插回后依然卡死**，说明卡死并非仅由"烧录闪断"引起，而是更普遍的 link-up 事件路径问题。

### 11.4 今晚 V4 的最终判定

- **V4 = 不通过 / 不能签收**（前向通路在设计层面不可用）。
- D1 从"锁存卡死"**改判为"末级数据/相位路径"**；D2（发射帧 dst=广播，违反 P2 单播契约）仍成立。
- T6/T7/T8、DROP 11 类、桥上界 = NOT_TESTED。
- iperf 双向超时（应用级佐证），桥上界仍 NOT_TESTED。
