# prj13 桥性能测试方案（D1/D2 修复后执行，iperf3 为主）

> 定位：**通路通了以后，iperf 是性能基线，是后续定协议的依据**（帧长/窗口/流控门限/重传策略）。
> 今晚（2026-11-19）桥双向不通（D1），iperf 只作连通性判据；本方案待 D1/D2 修复后执行。
> 纪律：性能数字必须与 pcap 字节级判据、板内计数**三方对齐**，不得单源引用。

| # | 条件 | 判据 |

## 1. 测量矩阵

### 1.1 UDP 吞吐 vs 负载长度（单向，A→B 与 B→A 各一轮）

```powershell
# 接收侧（PC2）：iperf3 -s -p 5201 -4
# 发送侧（PC1）：逐个长度，固定时长，逐级加压
foreach ($len in 64,128,256,512,1024,1472) {
  iperf3 -u -c 10.10.0.2 -p 5201 -b 50M -t 10 -l $len -4 --get-server-output
}
```

**同时**在对端抓包并跑字节级审计：

```powershell
py prj\project_13\pc\p13_pcap_audit.py --pcap <pcap> --port 5201 --src-mac 02:00:00:00:0a:01 --allow-dst 10.10.0.2
```

判据：`len_bad == 0`；`matched` 与 iperf3 报告的 datagrams **同量级**（iperf3 有丢包时允许差值，但必须两边都记录）。

### 1.2 丢包-速率曲线（找拐点，这条最能决定协议门限）

对每个长度，逐步提升 `-b`：`1M → 5M → 10M → 20M → 50M → 100M → 200M → 500M`，
记录 **发送速率 / 接收速率 / 丢包率 / 抖动**。拐点即"可持续吞吐"，是协议流控门限的输入。

### 1.3 双向并发

```powershell
# PC1 同时：A→B 与 B→A（两台各起双向）
iperf3 -u -c 10.10.0.2 -p 5201 -b 20M -t 30 -4 &
iperf3 -u -c 10.10.0.2 -p 5201 -b 20M -t 30 -4 -R
```

判据：两向同时满额、无乒乓（用 `p13_pcap_audit.py` 的 dst 白名单判据）。

### 1.4 并行流（协议是否要多队列的输入）

`-P 1 / 2 / 4 / 8`，同总带宽下比较丢包率：并行流丢包显著更低 ⇒ 单流受限于包处理，协议应支持多队列。

### 1.5 长稳（协议看门狗/超时参数输入）

单流固定速率跑 **≥600 s**，记录丢包随时间的漂移；配合板内 `mem_len_err`/`mem_stall`/`prev_drop` 的增量。

## 2. 判据与三方对齐

| 来源 | 取什么 |
|---|---|
| iperf3 客户端 | 发送速率、丢包率、抖动 |
| iperf3 服务端（`--get-server-output`） | 接收速率（**这才是真吞吐**） |
| pcap 字节级审计 | `cap==IP.len+14`、`len_bad`、`arp`、dst 白名单 |
| 板内 ILA | `pfwd_wr/pk_frames/up_frames/prev_wr/prev_drop` 增量 |

**对齐规则**：
- 接收帧数 ≈ iperf3 服务端 datagrams（允许 iperf3 统计窗口差异，差 >1% 必须解释）；
- `len_bad > 0` ⇒ 该轮数据**作废**，不得只引用 iperf3 数字；
- 桥上界 = 服务端接收速率的**拐点**，不是客户端发送速率。

---

## 3. 输出（喂给协议设计）

1. **可持续吞吐表**（按帧长 × 速率）；
2. **拐点表**（丢包率首次 >0.1% 的 `-b` 值）；
3. **并行流收益表**（`-P` 对比）；
4. **长稳漂移曲线**；
5. 明确的"限制来源"标注：主机侧 / 桥上 / 对端网卡 —— 三者必须分开写，**不得混为一个数**。

> 本晚已测得的 A 侧单板入向数据（`TPUT_BASELINE_A.md`）可作为 P5 主机基线的补充，
> 但**不能**当作桥上界——当时主机 Python 发送器卡在 ≈1745 fps。
