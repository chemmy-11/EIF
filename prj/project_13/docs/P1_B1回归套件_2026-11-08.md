# 1. P1-5 为什么要把 oneside/ctrl 扩成矩阵

prj12 的证据（`AUDIT_mechanism.md` §3.2）把缺陷机理拆成三分支，**由闪断那一拍 `rd_bin` 的残留值
`Q = 已弹出字节数 mod 8192` 决定**：

| Q 区间 | 占比 | 后果 | prj12 是否覆盖 |
|---|---|---|---|
| `Q ∈ [1,5633]` | ≈69% | **硬死锁**：`byte_room_ok` 恒 0 → `wr_hold` 粘滞 → 自锁 | ✅ `oneside` 只在 Q=465 这一点上覆盖 |
| `Q ∈ [5634,8191]` | ≈31% | **静默错位**：不锁死，但提交垃圾帧 / `len_err` 涨，同样不可自愈 | ❌ 从未覆盖 |
| `Q = 0` | 仅干净上电窗口 | **无害** | ❌ 从未覆盖（缺「触发条件边界」的反证） |

外加两个从未覆盖的维度：**反向（`u_mem2`，HAS_DMA=0）**（`AUDIT §7` 明确说「是未观测，不是免疫」）
与**连续多次闪断**（`FIX_PLAN.md` B1.5 第 7 步要求 5 次，但仿真里只做过 1 次）。

所以矩阵的 6 个场景不是「多跑几遍」，而是**把三个分支 + 反向 + 累积 + 对照各打一个点**。

# 2. 场景表（`sim/regress.ps1`）

## 2.1 参数化方式

`sim/p1_regress/tb_b1_matrix.v` 是**一个通用流程 + 4 个 plusarg**，不按场景写死代码（减少未编译代码量）：

| plusarg | 含义 |
|---|---|
| `PRE=n` | 闪断**前**发 n 帧（决定 Q = n×155 mod 8192） |
| `FLAPS=n` | 闪断次数 |
| `POST=n` | 每次闪断后发 n 帧 |
| `BOTH=0/1` | 0 = 只复位 user 域（现场 `aurora_rst` 真实接法）；1 = 两域同时复位（B1 的思路，对照组） |

> 一帧 154 B 的激励在 `frame_mem_if` 内变成 **155 个 wr_en 周期**，所以 `Q = PRE×155 mod 8192`
> （`PRE=3 → 465`；`PRE=37 → 5735`）。这条换算直接从 prj12 日志反推：3 帧后 `rd_bin=465`
> （`AUDIT_mechanism.md` §4.1 的 `T1_probe3` 快照）。

## 2.3 判据（6 条断言，名字即证据）

| 断言 | 内容 | 抓哪一类失败 |
|---|---|---|
| `A1_HEALTHY_BASELINE` | 闪断前 n 帧全部提交、`len_err=0`、`wr_hold=0` | 测试平台自身问题（不是 DUT bug） |
| `A2_EXACT_COMMITS` | 闪断后**恰好** POST 帧进 DDR（不多不少） | 少 = 硬死锁；**多 = 幽灵描述符重放** |
| `A3_NO_PERMANENT_HOLD` | `u_hold_cycles ≤ 200` | `wr_hold` 粘滞（接纳策略永久关闭） |
| `A4_LEN_ERR_UNCHANGED` | 真实 155 B 帧不得改变 `len_err` | 幽灵描述符（`wd_len=0`）被消费 |
| `A5_COMMIT_CONTENT_OK` | 每帧首字节 = 发送 seed、有效字节 = 155 | **静默错位**（Q∈[5634,8191] 分支，只有内容判据能抓） |
| `A9_RECOVER_BY_FULL_RESET` | 两域复位后写通路恢复 | 「唯一出口是 ui_rst_n」这一论断 |

`A2` 用「恰好」而不是「≥」是刻意的：静默错位分支会在真实帧之前/之间插入幽灵提交，
只有精确等值 + 内容比对才区分得开。`A5` 的实现是 TB 侧旁路采样 S2MM 流
（`dma_wr_tvalid/tready/tlast/tkeep`，`tb_b1_matrix.v` 的 `COMMIT CAPTURE` 段），
**不改 RTL**；`mem2` 版采样 `m_axi_wvalid/wstrb`。

### 2.6.1 缺陷机制的板上/仿真对账（负对照的指纹）

`oneside.neg` 的 `T2_after_flap` 快照与 prj12 `AUDIT_mechanism.md §4.1` **逐字段一致**：

```
[SNAP] T2_after_flap u_wr=0 u_drop=0 hold_cyc=397 wr_hold=1 |
       wr_bytes wr_bin=0 rd_bin=930 level=7262 | wr_desc wr_bin=0 rd_bin=0 |
       ui wr_frm=6 len_err=10 stall=0 ost=6 state=0
```

`wr_bin=0 / rd_bin=930 / level=7262 / wr_hold=1 / u_drop=3 / len_err=10 / state=0`
—— 即 `level = 8192 − Q`（`Q=465`，留 2FF 传播后为 930 字节）→ `byte_room_ok` 恒 0 → 自锁。
`mem2.neg` 给出**完全相同**的指纹（`rd_bin=930 level=7262`），这正是 `AUDIT §7` 预测但从未验证的对称性。

### 2.6.2 静默错位分支（`silent`）的实测：与预测一致，但**抓它的是 A2+A5，不是 A4**

`silent.neg`（`Q=5735`）：

```
[SNAP] T2_after_flap  wr_hold=1 | wr_bin=0 rd_bin=6277 level=1919 | wr_desc rd_bin=9 | state=2
[SNAP] T3_after_post_frames wr_hold=0 | wr_bin=310 rd_bin=7285 level=1217 | ui wr_frm=47
[INFO] flap 1: expected 3 commits, saw 10
[INFO]   frame 0: first_byte=72 bytes=155 (expect 80 / 155)
[ASSERT-FAIL] A2_EXACT_COMMITS / [ASSERT-FAIL] A5_COMMIT_CONTENT_OK
[ASSERT-PASS] A3_NO_PERMANENT_HOLD / [ASSERT-PASS] A4_LEN_ERR_UNCHANGED
```

- `level=1919 < BF_ROOM(2558)` ⇒ **不硬死锁**（`wr_hold` 在 T3 已回 0）—— 与「Q∈[5634,8191] 走静默错位」的预测**一致**；
- 但**提交了 10 帧而不是 3 帧**（幽灵描述符重放），且首字节是 `0x72/0x73/0x74`（上一轮的旧数据）而不是 `0x80/0x81/0x82`；
- `len_err` **保持 0**、`wr_hold` 不粘滞 ⇒ **A3/A4 在这个分支上是瞎的**，只有 A2（精确计数）+ A5（内容比对）能抓。

### 2.6.3 一个必须如实记录的发现：**A2 在硬死锁分支上会巧合通过，A5 是唯一两个分支都抓得到的断言**

| case | A2 精确计数 | A3 无粘滞 | A4 len_err | A5 内容 | 谁抓到了 |
|---|---|---|---|---|---|
| `oneside.neg` / `mem2.neg` | **PASS（巧合：3 个幽灵提交正好等于 3）** | **FAIL** | PASS | **FAIL** | A3 + A5 |
| `silent.neg` | **FAIL（10≠3）** | PASS（不锁死） | PASS（len_err=0） | **FAIL** | A2 + A5 |
| `multi.neg` | 第 1 次 PASS → 第 2 次起 FAIL | FAIL ×5 | PASS | FAIL ×5 | A2（第 2 次起）+ A3 + A5 |

⇒ **A5（提交内容 = 发送内容）是唯一在全部三个负对照里都失败的断言**，是这套判据的承重件；
A2 单独用会漏（硬死锁分支上幽灵提交数可能恰好等于真实帧数），A3 单独用会漏（静默分支不粘滞），

# 3. P1-6 全自动卡死看护（`scripts/stall_watchdog.ps1`）

## 3.1 判据（两个独立证据，缺一不可）

```
证据 1（ILA6，硬件域）：pfwd_wr 涨 ≥ -RaiseThreshold(默认3) 且 pk_frames 不变（16 位差分）
证据 2（UART，软核域）：mode=1 且 U 的 wdbg 字在两次相邻采样间**完全不变**
```

只看 `ch_up=1` 会误判 —— 2026-11-07 现场正是 `ch_up=1` 而 `pk` 已死（`FIX_PLAN.md` §方案 A′）。

状态机（`Get-WatchdogState`，纯函数、可离线自测）：

| 状态 | 条件 | 动作 |
|---|---|---|
| `LINK_DOWN` | `ch_up ≠ 1` | 不动作（链路掉 ≠ 卡死，等链路自己回来） |
| `NO_TRAFFIC` | `Δpfwd < 3` | 不动作（没有流量，无法判定） |
| `DATA_FLOWING` | `Δpfwd ≥ 3` 且 `Δpk > 0` | 不动作（数据面活着） |
| `SUSPECT_STALL` | `Δpfwd ≥ 3`、`Δpk = 0`，但 UART 缺失/wdbg 在动/mode≠1 | 不动作，继续采样 |
| `STALL_CONFIRMED` | 以上 + `mode=1` + wdbg 冻结 | **进恢复阶梯** |

`-StrictFingerprint` 追加「`wdbg` 低 16 位 = `last_commit_len` = 0」；
`-Ila3Confirm` 再追加 ILA3 的 `mem_len_err>0 && mem_stall==0 && mem_ost==0`（坑表指纹）。
默认关闭这两项的理由：多一次 ILA3 采集就多占一次 Vivado 会话，而 `wdbg` 冻结 + `pk` 冻结已经足够判定。

## 3.2 恢复阶梯（`-RecoverMode`）

| 值 | 动作 | 已知性 |
|---|---|---|
| `bitelf`（**默认**） | `twin_burn.ps1 -Board A -Mode BitElf -Run` → 串口 `d` → 3 帧探针 | 现场唯一验证过（60–90 s） |

## 3.5 dry-run 守卫：一次真实误触发与它的修复（纪律事件）

**事件**：2026-11-08 18:35:00，`stall_watchdog.ps1 -DryRun` **真的启动了一个 Vivado**。
证据 `out/evidence_2026-11-08_p1_suite/watchdog/ila6_poll_183500.console.log`：
`Xilinx cs_server v2023.1.0` → `connect_hw_server: elapsed = 00:00:08` →
`ERROR: [Common 17-39] 'get_hw_targets' failed` → 18:35:20 `Exiting Vivado`。

**为什么这是缺陷而不是笔误**：`-DryRun` 的契约是「只打印计划、不执行任何动作」。
在无板机器上它白起 ~20 s 的 Vivado，**占的正是全机串行的那个窗口**（当时另一个并行单元被迫等它）。

**根因**：旧代码在循环里**先取样、后判 `-DryRun`**，且没有统一的「拒绝启动外部进程」出口。

**修法（三层）**：

| 层 | 做法 |
|---|---|
| 1. 统一守卫 | 新增 `Test-CanLaunch`，**6 个外部启动点全部接入**：vivado ILA 抓取 / 串口 `U` / `xsct rst -system` / `twin_burn` / 串口 `d` / `py twin_send`。`-DryRun` 下打印 `DRY-NOEXEC: <内容>  [<完整命令行>]` 并返回「拒绝」，计数 `DRYRUN_REFUSED` |
| 2. 顺序前移 | `-DryRun` 分支移到**取样本之前**，并在分支内显式调用两次守卫，让日志**证明**拒绝路径生效 |
| 3. 自动断言 | `-SelfTest` 增 3 条：G1 守卫确实拒绝并计数；G2 本次日志**不出现** `Xilinx cs_server` / `Launch Output` / `Exiting Vivado`；G3 本次运行**没有**新生成 `ila6_*.console.log` |

> G2 的实现有个反身性陷阱：断言里**不能把这三个字样打印进日志**，否则断言自己会让日志失败。
> 所以日志里只写 `got=0 marker(s)`，样本文本刻意不打印 —— 代码注释里写明了原因。

**验收（2026-11-08 18:48:21 实测）**：

