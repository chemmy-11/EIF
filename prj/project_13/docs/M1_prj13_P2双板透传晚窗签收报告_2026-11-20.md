## 二、D1 根因与修复（本晚核心成果）

### 根因三条

| # | 缺陷 | 位置 |
|---|---|---|
| 1 | 不输出前导码/SFD（8 B） | `rtl/p2/eth_rewrap.v` 从 dst MAC 起始 |
| 2 | 不输出 FCS（4 B） | 全文 216 行仅 1 处提及 FCS，无 CRC 生成 |
| 3 | 出口 dst MAC 误用 `PEER_MAC` | 应为 `PC_MAC`（本板直连 PC） |

**控制变量证据**：同板同时段，栈帧（`crc32_d8` 自算 FCS）上线，转发帧（零 CRC）全丢。

### 修复（commit `cbfd304`）

```verilog
assign m_frame_len = tot_len + 16'd12;                              // +8 前导 +4 FCS
wire crc_en_w = out_ace && (state != S_FCS) && (state != S_PRE);    // CRC 只覆盖 MAC+IP+填充
assign m_eop  = (state == S_FCS) && (fcs_idx == 2'd3);
```

**FCS 取字节配方**（仿真验证，与板上已验证的 `rtl/arp/arp_tx.v:290-303` 同构）：
`~crc_data[24..31] / [16..23] / [8..15] / [0..7]`，各自 `rev8`。

### 离线回归（构建前闸门）

| 用例 | TB | 结果 |
|---|---|---|
| FCS 配方 4 组向量 | `sim/tb_crc32_fcs_order.sv` | **4/4 PASS** |
| 100 B UDP → 154 B | `sim/tb_eth_rewrap_fcs.sv` | **PASS（逐字节）** |
| 短帧填充 → 72 B | 同上 | **PASS** |
| 1500 B IPv4 → 1526 B | 同上 | **PASS** |

宽度 `72 / 154 / 1526` 与裁决给定 GMII 有效宽度一致。

### 上板验证（B 版，PC2 侧执行，PC1 复核）

**判据 1：`rgmii_tx_en_o` = 154 拍**

```
dbg_rgmii_tx_en_o  : 高 154 样本（512–665）
dbg_pump_rev_en    : 同样 154（完全同步）
stack_takeover / cmd_takeover / stack_txen : 0 × 1024
prev_rd : 0 → 1
```

**判据 2：首字节序列**

```
55 55 55 55 55 55 55 d5 | a8 2b dd 76 df a2 | 02 00 00 00 0b 01 | 08 00 | 45 00
└── 前导 7×55 + SFD ──┘ └── dst = PC2 网卡 ─┘ └─ src = 板 B ─┘ └IPv4┘
```
尾部末 4 字节 `eb 60 eb c5` = FCS。

**判据 3：pcap 3 帧逐帧**

```
cap=142  dst=a8:2b:dd:76:df:a2  src=02:00:00:00:0b:01  et=0x0800
         10.10.0.1 -> 10.10.0.2  udp 50726 > 47001     ×3
```

**⇒ T5 A→B = PASS（3/3）；D1 闭环；D2-relay 闭环。**

### 口径澄清（两层不可混）

| 层 | 长度 | 内容 |
|---|---|---|
| pcap（Npcap） | **142** | 14 以太头 + 20 IP + 8 UDP + 100 payload |
| GMII / `tx_en` | **154** | 142 + 8 前导 + 4 FCS |

判据应写「**pcap cap = IP.len + 14**」。

## 四、D3 新发现：突发超速致接收侧永久停摆

### 事件

18:29 PC1 为测发送端上限，用 `p2_rawsend --interval-ms 0` 打了 **20,000 帧 @1472 B（约 12,000 fps）**，持续 1.68 s。

| 位置 | 现象 |
|---|---|
| PC1 侧固件 | `drop = 17,347`（20,000 帧只收下 2,671） |
| **PC2 侧接收泵** | `up_frames = 11,851` 而 **`prev_wr = 0`** |

**⇒ 帧进了 Aurora 解包，一帧都没写进 RGMII TX 泵，且不自恢复。**

PC2 侧 180 s pcap 佐证：`board_mac_frames=0 / udp→47001=0 / udp→5201=0 / syn=0`。

### 缓冲深度量化

| 背靠背帧数 | 收下 | 丢弃 |
|---|---|---|
| 10 | 4 | **6** |
| 50 | 11 | 39 |
| 200 | 31 | 169 |
| 1000 | 152 | 848 |

⇒ **接收缓冲约 4 帧深**；背靠背间隔仅 12 µs（1 GbE 线速），48 µs 即填满。

### 与均匀发送的对比

| 发送方式 | 速率 | `drop_delta` |
|---|---|---|
| 均匀间隔（`--interval-ms`） | 1 / 2 / 5 / 10 / 15 / 20 / 25 Mbps | **全 0** |
| 均匀间隔，请求 40/60/80 Mbps（实际 ~18 Mbps） | ~18 Mbps | **全 0** |
| 背靠背连发 | 12,000 fps | 丢 87%，并打停对端 |

### 恢复方式

**重烧位流可恢复**（PC2 重烧 `135eb061` 后基线全 0，双向恢复正常）。
**重烧引起的链路闪断不致命**：18:24 PC1 重烧时 PC2 板仍正常（B→A 3/3）；18:48 PC2 重烧时 PC1 板软核重启但泵未停摆。

### 流程错误记录（PC1）

| # | 错误 | 后果 |
|---|---|---|
| 1 | 未通报即做 20k 帧洪泛 | 打停 PC2 接收泵，白耗约 20 分钟 |
| 2 | 把"无 SYN-ACK 无 RST"归因 PC2 防火墙 | 让 PC2 白查一轮防火墙配置（实际防火墙配置一直正确） |

## 七、协作方法教训

| 教训 | 说明 |
|---|---|
| **跨机 pcap 窗口必须 ≥180 s** | 对端是"定时轮询 + 收到即处理"，轮询周期约 1–2 min。60/70 s 窗口连续错过两次。 |
| **板侧计数是比 pcap 更可靠的证据** | pcap 会因窗口错位漏记，而 `up_frames`/`prev_wr` 持久累积，不受窗口影响。 |
| **先证板侧、再证链路层** | 本轮多次"pcap 0 帧"实为窗口问题，板侧计数一次就定位真相。 |
