## 1.1 为什么多尺寸要两种模式

`--expect-len` 是**白名单**（被抓到的长度必须 ⊆ 白名单），这是 `twin_recv.py:290-297` 的既有语义。
但它有个洞：**若 20 帧全是 100 B，其他 5 个尺寸一个都没到，白名单依然满足**。
所以矩阵判据额外提供 `--len-mode cover`（白名单里每个长度都必须至少出现一次），
用于"多尺寸到齐"这种**覆盖型**判据；`subset` 保留用于单尺寸窗口。
两者都有 mock 用例覆盖（矩阵 #18/#19/#20）。

## 1.2 地址 scheme 与位流配对（2026-11-08 项目负责人裁决）

**scheme 是 PC 侧的地址表，不是板卡的属性**：板卡的 IP/MAC 硬编码在位流 RTL 里
（P1 基线定死 `192.168.1.10` / `00:11:22:33:44:55`）。所以必须**先看烧的是哪颗位流，再选 scheme**，
不能反过来按 scheme 去改板。

| scheme | 配对的位流 | 板 IP（A / B） | 板 MAC（A / B） | 定位 | `p1_selfcheck.ps1` |
|---|---|---|---|---|---|
| **`p1`** | **P1 基线**（bit `C856BA83…` + ELF `BA3C0220…` + `prj12\scripts\probes.ltx`） | `192.168.1.10` / 同 | `00:11:22:33:44:55` / 同 | 现役位流；**M1 复现的对象** | **默认** `-IpScheme p1` |
| `handbook` | prj13 出片后的 **P2 候选** | `10.10.0.11` / `10.10.0.12` | `02:00:00:00:0A:01` / `02:00:00:00:0B:01` | 开工手册 §8 建议、P2/M2 的**默认** | `-IpScheme handbook`（会打 `EXPECT P2 BITSTREAM`） |
| `protocol` | v0.2 契约（历史） | `192.168.50.11` / `192.168.50.12` | 同 handbook | **仅历史参考**，不再用于新实验 | `-IpScheme protocol`（同样打 `EXPECT P2 BITSTREAM`） |

**烧错 scheme 的症状（最容易误判成链路故障）**：

- 链路判据**全部 PASS**：`link_ok=1 ch_up=1 lane_up=1 gt_pll_lock=1 hard=0 soft=0`；
- 数据面**静默全丢**：抓包 `matched=0 / other=20`（帧根本没发到板卡，或板卡回的帧 MAC 不在候选里），
  判据给 `JUDGE: FAIL … frames=0 … loss=FAIL(20 missing)`；
- 板侧计数**不涨**：`pfwd_wr` / `pk_frames` / `up_frames` 全冻结（因为板卡根本没收到）。

⇒ 看到"链路好、一帧都收不到、计数不涨"，**先查 scheme 与位流是否配对**，不要去拆链路/换光纤/重烧。

**三个自检钩子（`p1_selfcheck.ps1` 启动即打印，必须与所烧位流一致）**：

```
ADDR_SCHEME p1 (P1 baseline bitstream 192.168.1.10); use -IpScheme handbook after a P2 bitstream is burned
ADDR_TARGET board A -> 192.168.1.10:1234/udp, judge src-mac=00:11:22:33:44:55 (from -IpScheme)
ADDR_PASSTHROUGH twin_send.py --scheme p1 --pair A | twin_recv.py --scheme p1 --pair A | static_arp.ps1 -Scheme p1 -BoardPcPair A
```

`-IpScheme` 是**显式透传**：`twin_send.py --scheme` / `twin_recv.py --scheme` / `static_arp.ps1 -Scheme`
（STEP 3b）全都用同一个值；`p1_judge.py` 的 `--board-mac` 也由 scheme 推导（`p1`→`00:11:22…`；
`handbook`/`protocol`→ 该板新 MAC）。选 `handbook`/`protocol` 时额外打 `EXPECT P2 BITSTREAM …`，**不阻断但留痕**。

**防漂移**：脚本里的 scheme 表是 `pc\twin_send.py` `SCHEMES` 的镜像。启动时脚本会离线跑一次
`py pc\twin_send.py --dry-run --scheme … --pair …`（不发包），把它的 `dst` / `eth dst` 与自己的表逐字段比对，
一致打 `PRECHECK addr-sync : ok (…)`，不一致打 `MISMATCH` 并提示**先修表再烧**。

判据侧：`p1_judge.py` **只认 `eth.src` + payload + 端口 + `run_id`，从不读 IP 字面量、从不看 `eth.dst`**，
所以换地址方案不会悄悄改判定；唯一 scheme 相关的输入是板卡 MAC，其默认候选集已同时覆盖
`00:11:22:33:44:55`（p1）与 `02:00:00:00:0A:01 / 0B:01`（handbook/protocol），
要严格单 scheme 时用 `--board-mac` 收窄（矩阵 #26/#27 就是这两条的正反例）。

## 2.2 两台 PC 的窗口对齐

手册 §4 的固定时钟槽，在本脚本里落地成两条约束：

1. 每个方向是**一次连续 180 s 抓包**，发送落在窗口内 T0+30 s（`-SendDelaySeconds`）；
2. 收发角色由 `-Board` 决定（板 A 发 `0x1`、板 B 发 `0x2`），**方向不同则角色不同**：

| 窗口 | 板 A（PC1） | 板 B（PC2） |
|---|---|---|
| 窗口 1（`fwd`，run_id `0x1`） | T0+30 s 发 20 帧（20 ms） | 连续抓 180 s → 判 `0x1` |
| 窗口 2（`rev`，run_id `0x2`） | 连续抓 180 s → 判 `0x2` | T0+30 s 发 20 帧（20 ms） |
| 窗口 3（`10mib`，run_id `0x1`） | T0+30 s 发 7125 帧 1472 B（`-SendIntervalMs`，默认 0.5 ms ≈3.6 s） | 连续抓 180 s → 判 `0x1`（`--expect-count 7125`） |

两台 PC **同时启动**脚本（烧录耗时抖动约 10–30 s，窗口 180 s / 发送在 +30 s，容差很宽）。
若抖动更大，用 `-Step6DelaySeconds N` 让先到的那台等一等。
单机验证时用 `-LocalDir none`：两个方向都抓都判（需对端在各自窗口内发包）。

## 2.3 `scripts\p1_judge.py`

```powershell
py scripts\p1_judge.py --from-pcap out\rx.pcap --board-mac 00:11:22:33:44:55 `
   --port 1234 --port-direction any `
   --expect-count 20 --count-mode exact `
   --expect-len 26,64,100,512,1024,1472 [--len-mode subset|cover] `
   --expect-run-id 0x1 --allow-dup 0 [--json-out out\judge.json]
```

| 参数 | 默认 | 说明 |
|---|---|---|
| `--from-pcap` | 必填 | 经典 pcap 或 pcapng（`linktype=1`） |
| `--board-mac` | `00:11:22:33:44:55` | 可重复给多值（两块板 MAC 相同也应显式给） |
| `--port` / `--port-direction` | `1234` / `any` | `any` = sport 或 dport 命中 |
| `--expect-count` / `--count-mode` | `0` / `exact` | 0 = 不判；`min` 是 `twin_recv` 的旧 `>=` 语义 |
| `--expect-len` / `--len-mode` | 空 / `subset` | 白名单多值；`cover` 要求每个长度都出现 |
| `--expect-run-id`（别名 `--run-id`） | 空 | 可用 `0x1`、`1`；多值=子集语义 |
| `--allow-dup` | `0` | 容忍的重复 seq 数（`--allow-dup 0` 与裸 `--allow-dup`=1 都支持） |
| `--no-check-total` | — | 关掉"payload 的 `count` 字段必须等于 `--expect-count`" |
| `--print-frames` | `20` | 逐帧明细条数；`0`=全列（超出时会明确写"还有 N 帧未逐条列出"） |
| `--json-out` | 空 | 落一份机读判定 JSON（含 throughput/stats/checks） |

**退出码**：`0`=PASS、`1`=FAIL、`2`=参数/文件/格式错误。
**末行固定**：`JUDGE: PASS|FAIL key=frames=… count=… unique=… dup=… fill=… len=… runid=… total=… payload=… loss=…`，
FAIL 时另打 `CHECK-FAIL: <key>=FAIL(…)`。

## 2.4 多尺寸矩阵与 10 MiB 的具体命令（上板时逐条执行）

```powershell
# 6 个尺寸 × 20 帧，每尺寸两方向各一条；窗口内先起抓包再发（不要分块）
$sizes = 26,64,100,512,1024,1472
foreach ($L in $sizes) {
    py pc\twin_send.py --dst-ip 192.168.1.10 --dst-port 1234 --count 20 --len $L --run-id 0x1 --interval-ms 20
    py scripts\p1_judge.py --from-pcap out\rx_fwd_$L.pcap --board-mac 00:11:22:33:44:55 --port 1234 `
       --port-direction any --expect-count 20 --expect-len 26,64,100,512,1024,1472 --expect-run-id 0x1 --allow-dup 0
}

# 10 MiB 单向：1472 B × 7125 帧（total 字段必须也是 7125 -> --count 7125）
# 注意 --interval-ms：STEP 6 的 10 MiB 段已把它参数化（`-SendIntervalMs`，默认 0.5 ms）。
# 默认 20 ms 时 7125 帧要 142.5 s，加 30 s 发送延迟 = 172.5 s，180 s 窗口只剩 7.5 s 余量；
# 软核逐帧 DMA 上限约 23 Mbps（指南 §6.1 路线 B）≈ 1950 pps ≈ 0.51 ms/帧 -> 默认 0.5 ms 正好贴住。
py pc\twin_send.py --dst-ip 192.168.1.10 --dst-port 1234 --count 7125 --len 1472 --run-id 0x1 --interval-ms 0.5
py scripts\p1_judge.py --from-pcap out\rx_10mib.pcap --board-mac 00:11:22:33:44:55 --port 1234 `
   --port-direction any --expect-count 7125 --count-mode exact --expect-len 1472 --expect-run-id 0x1 `
   --allow-dup 0 --print-frames 5 --json-out out\judge_10mib.json
```

# 6. 风险与限制

1. **实跑路径未上板验证（L1）**：STEP 2–6 的非干跑分支只做了参数级与命令级校验；
   其中 `Start-Process`/`WaitForExit` 的抓包编排、`ILA CSV` 表头解析（`Read-IlaCsv`）都在真实板上才会被真正走到。
   上板第一次跑务必看每一步的 `CMD:` 与 `csv=` 路径是否如预期。
2. **跨工程借用 helper**：`twin_burn.ps1` 只在 prj12 有 → 会烧 **P1 基线对**（`C856BA83` + `BA3C0220`）。
   M1 复现的对象正是这对基线，所以本轮**不建** `prj13\out\twin_config.json`（避免造成"以为烧了 prj13 新位流"）。
   prj13 一旦出片（P2 候选），必须先建 `prj13\out\twin_config.json` 回填 `expect_bit_sha256`、换配对的 `probes.ltx`，
   再用 `-PrjRoot D:\FPGA\prj\project_13` 跑；否则**烧的仍是基线** —— 见 §4 清单 **0c** 的三行 precheck 核对。
3. **板 B 配置仍是 `<FILL>`**：prj12 `twin_config.json` 里板 B 的 `jtag_serial`/`com`/`pc_nic` 未填 →
   `-Cable` 与 `-Iface` 必须人工给（脚本已传 `-Cable`，`-Iface` 需现场给）。
4. **判据不校验 IP/UDP 校验和**：板卡透传不改 IP 头；PC 侧网卡已裁掉坏帧。要查需另开判据。
5. **10 MiB 的坡度**：`twin_send.py` 默认 `--interval-ms 20`（`pc\twin_send.py:49`）→ 7125 帧要 142.5 s，
   加 30 s 发送延迟已到 172.5 s，180 s 窗口只剩 7.5 s 余量；**已参数化为 `-SendIntervalMs`（默认 0.5 ms ≈3.6 s）**，STEP 6 的 10 MiB 窗口与 dry-run 的 `CMD:` 行都用它（双向 20 帧段仍固定 20 ms）。
   10 MiB 能否过，最终受软核逐帧 DMA 上限（≈23 Mbps，指南 §6.1 路线 B）约束 ——
   这一条属于 P0-4（PC 侧吞吐基准）与 P1-8（硬件批量路径），本判据只负责"0 丢 0 重 + fill 全 ok"。
6. **mock 时间戳是合成的**：见 §3.4。
7. **地址 scheme 与位流不配对的静默失败**（2026-11-08 新增风险位）：`-IpScheme handbook` 打在 P1 基线位流上，
   或 P2 位流配 `p1`，症状是"链路全 PASS、数据面一帧不收、板侧计数不涨"。这不是链路故障，
   诊断顺序见 §1.2；脚本已用 `ADDR_SCHEME` / `ADDR_TARGET` / `PRECHECK addr-sync` 三行留痕。
