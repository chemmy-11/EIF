### 烧录坑（两端都踩，已固化为判据）

`burn_one.tcl:29 connect` 报错，而 **xsct 的 exit code 仍为 0**（假象）。

- 根因：Vivado 自带的 `hw_server` 随 Vivado 退出而结束；`xsct` 的 `connect` 要求它常驻
- 解法：先 detached 起 `hw_server.bat`，确认 3121 在听，再烧
- **判据：只认 `BURN_OK` 那一行，不看 exit code**

另：**断纤态串口无应答**（实测 `COM5` 发 `I` → `NO_RESP`）⇒ 烧完读不到 `now=DMA` 属正常，插纤后一次即 `PASS`。这条推翻了开工时"先 DMA 后插纤"的错误协议。

### 4.3 端到端 — `NOT_TESTED`，且三种自证法均被混淆因素废掉

| 方法 | 结果 | 为何不可用 |
|---|---|---|
| `ping 10.10.0.11`（板自答） | 3/3 | 只证明板卡栈正常，不过 Aurora |

## 5. 新发现：D2（发射帧 dst = 广播）在决策 C 位流上复现

PC1 数据网卡（`以太网`）计数器：

| 项 | 值 |
|---|---|
| `ReceivedUnicastPackets` | **0** |
| `ReceivedBroadcastPackets` | 162,830（`ping 10.10.0.11` 后 **+3**） |
| 静止期 10 s 增量 | 0（无风暴） |

`ping` 的 3 个应答**未进单播计数**而进了广播计数 ⇒ 板卡发射帧 dst MAC = `ff:ff:ff:ff:ff:ff`。

**这是 11-19 D2 在新位流上的独立复现（从网卡计数器角度，不依赖 pcap）。**

影响与口径：
- 正式轮的**单播判据**（`--no-bcast` + `--expect-dst-mac`）**必然失败**
- **不得用单播口径否掉通路**；广播/单播两种口径**分开落账**
- 该缺陷不影响 iperf 的连通性与吞吐测量本身（UDP 吞吐不依赖 dst MAC 单播性）

## 8. 今日方法论沉淀（可直接复用到下一窗口）

1. **烧录判据只认 `BURN_OK`**，xsct exit code 不可信；先起 hw_server 再烧。
2. **拔纤 → 双端烧 → 插纤** 是当前最优启动顺序；插纤后再置 DMA。
3. **`LINK_HEALTH` 先读、再置 DMA** —— 让告警基线早于中间链路事件。
4. **发送侧必须做零点对账**（发前/发后各抓一次 ILA），否则增量会被 ping 等旁路流量污染
   （本次 `mem_wr_frm=7` 就是 4 ping + 3 twin 的合成，若不做零点对账会被误读成"多发了几帧"）。
5. **端到端不能靠 ping/TCP 自证**：本设计板卡无 TCP 栈、两端 Windows 默认不回 ICMP。
   唯一干净判据是对端 RTL 计数器。
