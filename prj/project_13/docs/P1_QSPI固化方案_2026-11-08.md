# 1. 容量与压缩评估

## 1.1 输入数字（本机实测）

| 项 | 字节 | 来源 |
|---|---|---|
| N25Q128 容量 | **16,777,216** | 128 Mbit = 16 MiB（板卡 flash 型号 `n25q128-3.3v-spi-x1_x2_x4`） |
| P1 基线位流 `C856BA83…7401` | **10,302,552** | `prj12/out/aurora_mem_bridge.bit`（`Get-Item .Length` 实测） |
| B1 候选位流 `b1_E9BE2B14` | **10,636,592** | `prj13_P2开工手册 §1` |

## 1.2 占用率（脚本自动算）

```
基线 : 10,302,552 / 16,777,216 = 61.4%   余量 6,474,664 B (6.17 MiB)
B1   : 10,636,592 / 16,777,216 = 63.4%   余量 6,140,624 B (5.86 MiB)
```

**结论**：两种位流都能单镜像整片烧写，不需要压缩、不需要多镜像/回滚槽。

## 1.3 `.mcs` 体积怎么估（别把宿主机文件当成 flash 占用）

Intel-HEX 风格 `.mcs` 每行最多 16 个数据字节：

```
:LLAAAATT<32 个 hex 字符>CC\r\n
= 1(:) + 2(LL) + 4(AAAA) + 2(TT) + 32(data) + 2(CC) + 2(CRLF) = 45 字节 / 16 数据字节
```

```
基线 : ceil(10,302,552/16) = 643,910 条 -> 643,910 × 45 + 16 ≈ 28,975,966 B ≈ 27.6 MiB
B1   : ceil(10,636,592/16) = 664,787 条 -> 664,787 × 45 + 16 ≈ 29,915,431 B ≈ 28.5 MiB
```

- 这个文本只是**磁盘文件**；`program_hw_cfgmem` 解析后只把 **payload**（10.3/10.6 MB）写进 flash，
  所以 flash 占用 = §1.2，不是 27.6 MB。
- 若真要存成「raw 镜像直接写 flash」，28 MB > 16 MB 就放不下了 —— **这是唯一会踩的坑**，
  所以脚本只走 `program_hw_cfgmem`（解析型），不走「把 .mcs 当二进制灌」的路子。
- 实测值以构建日志 `CFGMEM_MCS_BYTES` 为准（本方案未跑构建，故只有估算）。

## 1.4 压缩（`-Compress`）

- `write_cfgmem ... -compress` 会生成压缩位流（UltraScale 支持）。设计主体是 LUT/FF/BRAM 混合，
  压缩率**未实测**，经验区间 1.2×–2×，但**本方案不依赖它**。
- 只有当未来位流涨到 >16 MB（例如 P2 加大量 BRAM 调试或换更大器件）时才需要重新评估。
- **风险**：压缩后的镜像要求 boot 时解压，若 flash 时序/时钟余量不足可能出现「偶发加载失败」，
  表现为上电后 `get_hw_ilas=0` 但重烧 JTAG 正常 —— 那时先回退到非压缩镜像。

# 2. 脚本与用法

## 2.1 两个文件的分工

| 文件 | 职责 | 闸门 |
|---|---|---|
| `scripts/write_cfgmem.tcl` | **所有 Tcl 侧动作**（build / backup / program 三模式）。一个文件便于过语法闸 | Tcl 8.5.14 `tcl-check.ps1` **PASS** |
| `scripts/qspi_program.ps1` | 参数校验、容量评估、串行保护、调用上面的 Tcl、解析 marker、boot 后验收 | 纯 ASCII + PS 5.1；`evaluate/dry-run` 全档自检 |

**为什么把 Tcl 集中成一个文件**：本环境下 Vivado 的 Tcl 是 8.5.14，任何生成式 Tcl（PowerShell here-string 拼出来的脚本）
都没法在离线状态过语法闸，只能等上板当天才知道好不好使。集中成一文件 = 交付前就能 PASS。

## 2.2 `write_cfgmem.tcl` 三模式

```tcl
# 1) 造镜像（宿主机，不碰硬件）
vivado -mode batch -source scripts\write_cfgmem.tcl -notrace -tclargs ^
    build <bit> <mcs> <size_mb> <interface> [compress]

# 2) 备份 flash（读，危险度低但要板）
vivado -mode batch -source scripts\write_cfgmem.tcl -notrace -tclargs ^
    backup <out_file> <size_mb> <interface> <flash_part> [hw_server] [cable]

# 3) 烧写 + 从 flash 启动（**破坏性**）
vivado -mode batch -source scripts\write_cfgmem.tcl -notrace -tclargs ^
    program <mcs> <size_mb> <interface> <flash_part> [hw_server] [cable]
```

关键行（`write_cfgmem.tcl:150` 附近，build 模式）：

```tcl
set lb "up 0x0 $bit"
write_cfgmem -format mcs -interface SPIx4 -size 16 -loadbit $lb -force $mcs
```

`up 0x0` = 写到地址 0，即 SPI boot ROM 上电读取的起始地址。

关键行（program 模式）——**四件套属性**：

```tcl
create_hw_cfgmem -hw_device $dev $part_obj
set_property PROGRAM.FILES       [list $mcs] $cfg
set_property PROGRAM.ERASE       1           $cfg
set_property PROGRAM.CFG_PROGRAM 1           $cfg
set_property PROGRAM.VERIFY      1           $cfg
program_hw_cfgmem -hw_cfgmem $cfg
boot_hw_device $dev
```

`PROGRAM.VERIFY 1` 是写入后的读回比对 —— **这是唯一自动的写入完整性检查**，不要关。
`PROGRAM.ERASE 1` 会擦整片（不是按扇区），所以「只改一部分」是不可能的，每次都是全镜像重写。

**flash part 字符串**：默认 `n25q128-3.3v-spi-x1_x2_x4`。脚本会先打印
`get_cfgmem_parts` 的**完整列表**（`CFGMEM_PART: …`），解析不到就打印
`CFGMEM_PART_RESOLVE_FAIL` 并退出 —— 不允许「猜一个型号烧」。

## 2.3 `qspi_program.ps1` 五档

```powershell
cd D:\FPGA\prj\project_13

# 0) 纯宿主机评估（不启 Vivado）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\qspi_program.ps1 -Mode evaluate

# 1) 造 mcs（宿主机 Vivado，非硬件会话）
powershell ... -Mode build -Run

# 2) 备份出厂镜像（**必须在 program 之前**）
powershell ... -Mode backup -Run

# 3) 烧写（破坏性：必须 -Run + -FlashWrite 双闸）
powershell ... -Mode program -Run -FlashWrite -Verify

# 4) 一条龙（build -> backup -> program -> verify）
powershell ... -Mode pipeline -Run -FlashWrite -Verify
```

双闸设计：`-Run` 只放开「宿主机/只读」动作（build、backup），
**`-FlashWrite` 才能擦写 flash**。默认两闸都不给 = 只打印计划。
这与 `twin_burn.ps1` 的「默认 dry-run」约定一致（`prj12/out/twin_burn.ps1:1-14`）。

# 3. 出厂固件备份与回滚

## 3.1 为什么必须先备份

板子出厂时 flash 里是**厂商/上一手留下的镜像**（坑表：`get_hw_ilas=0` 的那个设计就是它驱动的，
它也会驱动 GE2 网口，所以「网口 Up」不能证明我们的位流在跑）。
一旦擦掉，**没有人能凭空恢复那个镜像** —— 只能靠读回。

## 3.2 备份手段与可行性（诚实分级）

| 手段 | 可行性 | 状态 |
|---|---|---|
| `readback_hw_cfgmem`（Vivado 原生读回） | **取决于 2023.1 是否提供该命令**。脚本已用 `info commands readback_hw_cfgmem` 探测，缺失则 `exit 3` | **未验证**（本轮禁启 Vivado 硬件会话） |
| 上板前先记下 flash 里到底是不是出厂镜像（`get_hw_ilas` 数量 + 链路行为指纹） | 只能**证明是不是**，拿不到字节 | 只能定性 |
| 用逻辑分析仪/独立 SPI 主机直接读 flash | 需要额外硬件、且要拆板/飞线 | 不可行（本阶段） |
| 放弃备份、只保证「能救回可用态」 | 可行（JTAG 独立） | ✅ 兜底 |

**协议**：`write_cfgmem.tcl` backup 模式在能力缺失时打印

```
CFGMEM_BACKUP_UNSUPPORTED: this Vivado has no readback_hw_cfgmem command
CFGMEM_BACKUP_UNSUPPORTED_ADVICE: do NOT overwrite the flash until a known-good image exists on disk
```

并 `exit 3`；`qspi_program.ps1` 随之打印 `QSPI_RESULT: BACKUP_UNSUPPORTED` 并 **停止 pipeline**。
也就是说：**备份拿不到，pipeline 就不会往下烧** —— 这时候必须由人对「样本板出厂镜像不可恢复」明确点头，
才允许单独跑 `-Mode program -Run -FlashWrite`。

## 3.3 备份文件命名

- 默认 `prj13/out/flash_backup_<yyyyMMdd>.bin`
- **注意**：`readback` 得到的通常是器件**原始字节流**，不是可解析的 Intel-HEX `.mcs`，
  所以默认用 `.bin`。任务书里写的 `flash_backup_<date>.mcs` 可用
  `-BackupFile D:\...\flash_backup_20261108.mcs` 强制命名，但请知道**扩展名不代表格式**。
- 归档纪律：备份文件大（≈16 MB raw 或更大），**不入 git**，按 `SHA256 + 路径` 登记
  （与 `.bit/.ltx/.pcap` 同一规则，`prj12_双板上板操作手册 §7`）。

## 3.4 回滚命令

```powershell
# 回滚 = 把备份镜像原样写回去（pipeline 之外单独跑，避免又把 backup 覆盖掉）
powershell -NoProfile -ExecutionPolicy Bypass -File scripts\qspi_program.ps1 ^
    -Mode program -Run -FlashWrite ^
    -Mcs D:\FPGA\prj\project_13\out\flash_backup_20261108.bin

# 若 readback 结果是 raw bin，program 模式需要 .mcs 才能被 write_cfgmem 体系接受 ->
# 这时先用 Vivado 把 raw 包成 mcs（等上板确认 readback 的真实格式后再定，见 §6 待确认 1）
```

**如果连 flash 都写不进去**（回滚也失败）→ 走 §4 的 R1/R2。

# 4. 风险：烧错之后怎么救（恢复阶梯）

| 级别 | 现象 | 处置 | 预计耗时 | 依据 |
|---|---|---|---|---|
| **R1** | 烧写中断/镜像错 → 上电不启动（`get_hw_ilas=0`），但 **JTAG 还能认到器件** | JTAG 直接烧 SRAM 位流：`out\twin_burn.ps1 -Board A -Mode Bit -Run` → 板子立刻可用；再重造 mcs 重烧 flash | 1–3 min | JTAG 配置不依赖 flash 内容 |
| **R2** | 连 JTAG 也认不到（boot mode 被 flash 卡住 / 器件不进边界扫描） | 用板卡 **MODE 拨码/M[2:0]** 强制 JTAG 模式后重试 R1 | 5–15 min | **依赖板卡原理图，本方案未确认拨码位置**（§6 待确认 2） |
| **R3** | flash 芯片物理损坏 | 换芯片 / 返厂 | 天级 | 极端情况 |

**关键判断：烧错不会「砖」到没法救** —— 最坏也只是「flash 里的镜像没用」，SRAM 配置路径始终在。
真正不可逆的只有**出厂镜像**（§3），所以 §3 的备份是唯一硬约束。

**烧写过程中的风险（比烧错更现实）**：

- **板 B 的无规律复位（issue #15，2026-11-06 共 10 次，间隔 2–38 min）**：`program_hw_cfgmem`
  期间若板子掉电/复位，镜像可能只写了一半。`PROGRAM.VERIFY 1` 会在结束时读回比对，
  比对失败 → `CFGMEM_PROGRAM_FAIL` → 按 R1 救。
- 所以：**先烧板 A（稳定），流程跑顺了再烧板 B**；板 B 建议在「刚换过电源/接触件且连续 ≥30 min
  没复位」的窗口里做（对应 issue #15 的验收口径 60 min 不掉链）。
- 反面意见（也写下来）：正因为板 B 复位多，**固化对它的收益最大**（复位后自动加载，不再需要人工重烧）。
  两条都成立 —— 结论是「先 A 验流程、再 B 吃收益」。

# 6. 验收与待确认

## 6.1 验收标准（烧写后）

| 判据 | 期望 | 怎么测 | 注意 |
|---|---|---|---|
| 上电 30 s 内位流加载 | `get_hw_ilas = 4` | `scripts\ila_capture.tcl` 或 Vivado `get_hw_ilas` | **只看 ILA 个数**；`CONFIG_STATUS`/`s2sr`/`wmwr` 无判别力（坑表） |
| 链路起来了 | `ch_up=1 / lane_up=1 / gt_pll_lock=1 / aurora_rst=0` | ILA6 单帧 | 与 P1 判据一致 |
| 数据面可用 | 3 帧探针 `pk_frames +3` | `py pc\twin_send.py --count 3 --len 100 --run-id 0x91` | flash 启动后仍需串口 `d`（ELF 在 flash？见 §6-3） |
| 掉电重来 | 断电 10 s → 上电 → **不烧任何东西** → 30 s 内 `ilas=4` + `ch_up=1` | 同上 | **这才是固化的意义** |
| 写入完整性 | `PROGRAM.VERIFY 1` 通过（`CFGMEM_PROGRAM_OK`） | 脚本日志 | 失败即 R1 |

脚本已实现第 1/2 条的自动判定：`-Verify` 会轮询 `-VerifyWindowSec`（默认 30 s），
抓 ILA6 并要求 `dbg_ch_up=1`，打印 `FLASH_VERIFY: PASS/FAIL`。

## 6.2 待确认（**不要自己拍板**）

1. **`readback_hw_cfgmem` 在 Vivado 2023.1 里到底有没有** —— 上板第一件事用 Tcl 控制台
   `info commands readback_hw_cfgmem` / `help readback_hw_cfgmem` 确认；返回的到底是 raw bin 还是 mcs，也要实测。
2. **板卡 boot mode 引脚（M[2:0]）定义** —— 查原理图；这决定 R2 能不能执行。
3. **固化后 ELF 从哪来** —— 当前软核程序是 JTAG `dow` 下的（易失）。若只固化 `.bit`，
   上电后**固件不在**，需要重新 `twin_burn -Mode BitElf -Run`（那就失去固化意义）。
   → 真正的「上电即用」需要把 ELF 也放进 flash 并由位流搬运，或改成 BRAM 初始化（`-Mode BitElf` 的一次性方案）。
   **这是本方案最大的未解项**，影响「固化收益」的表述：本方案目前只能验收「位流自动加载」，
   不能验收「数据面自动可用」。
4. 压缩镜像的加载稳定性（需实测 `-Compress` 后的上电成功率）。
5. flash 写入速度/耗时未实测（用于排窗口）。
