## 3. 机制分析

### 3.1 判据链：为什么「报头满额但线上短 64」指向板侧 TX

| 步 | 观测 | 推论 |
|---|---|---|
| 1 | 帧被截到 cap=78，但同帧 `IP.total_length` / `UDP.length` 是**满额正确值**（如 cap=78 而 IP.len=128） | 截断发生在 **IP/UDP 报头生成之后** ⇒ 不是软件层的帧构造或长度计算问题 |
| 2 | 11-12 pcap 复核：`origlen == caplen` **全为 0 差**（`0x103` 78/78、`0x106` 1450/1450、`0x111` 78/78、`0x1A0` 1178/1178） | 网卡交给抓包栈的就是这个短帧 ⇒ **线上帧本身就短**，缺字节在发送端 MAC 之前/之中完成 |
| 3 | 短的长度恒为 **64 B**，与帧长无关（78/490/1002/1178/1450 五个尺寸全部 −64） | 不是整帧丢失、不是按比例丢包，而是**帧尾固定一个 64 B 单位未上线** ⇒ 指向 TX 尾块的取数/写出 |

⇒ 三条合起来：缺字节发生在**发送板 TX 侧**，与接收主机、抓包工具无关。

### 3.2 排除「抓包侧截断」

- `npcap_capture.py:124` —— `ap.add_argument("--snaplen", type=int, default=65535)`，默认值 65535 远大于最大线上帧 1514 B。
- `m1a_sweep.py:112` —— 组装抓包命令 `cap_cmd = [PY, CAP, "--iface", …, "--seconds", …, "--out", pcap]`，**未传 `--snaplen`** ⇒ 走默认 65535。
- 正面证据：`origlen == caplen` 全为 0 差。若是 snaplen 截断，`origlen` 应为线上原长（1514/1242）而 `caplen` 为 65535 之下的小值，两者必然不等。
- **判定：排除。**

### 3.3 排除「报头字段错 / 判据工具系统偏差」

- 短帧的 `IP.total_length` / `UDP.length` 是满额正确值（cap=78 而 IP.len=128）⇒ 报头不是按短帧算出来的，不存在"报头也一起少 64"的情形。
- 若为判据工具（长度计算方式）错，11-19 用**同一台 PC1、同一判据工具**不可能 315 帧全部满足 `cap == IP.len + 14`。
- **判定：排除。**

### 3.4 排除「位流确定性缺陷」

- 11-19 复测用的是**同一颗** B1：`out/b1_E9BE2B14/aurora_mem_bridge_b1.bit`，SHA256 `e9be2b14…308e`，10,636,592 B，构建 **2026-11-07 23:12:34**（早于 11-12，故 11-12 用的就是它）。
- 11-12 侧另有独立核对：`pc1_prep_20261112.txt` §2 明写「B1 三件套哈希（复算 MATCH）」。
- 11-19 该位流出 A→B **120 帧全满额**。
- 确定性缺陷的定义是"同一位流、同一设计，重复运行必然复现"。同一颗位流 11-12 复现、11-19 不复现 ⇒ **非确定性缺陷**。
- **判定：排除。**

### 3.5 排除「共享 RTL 逻辑缺陷」

| 共享文件 | prj12 vs prj13 SHA256 |
|---|---|
| `async_fifo.v` | 逐字节相同 |
| `frame_mem_if.v` | 逐字节相同 |
| `axis_word_unpack.v` | 逐字节相同 |
| `axis_word_pack.v` | 逐字节相同 |
| `frame_fifo_pump.v` | 逐字节相同 |
| `aurora_udp_bridge.v` | 逐字节相同 |
| `cmd_channel.v` | 逐字节相同 |

- 逻辑缺陷是确定性的：同一份 RTL 若含 −64 B 的逻辑错，**今日必复现**。
- 今日 315 帧 0 失配 ⇒ **不是共享 RTL 逻辑缺陷**。
- **判定：排除。**（残余位置只剩"物理板配对 + 主机/PHY 状态"这一层。）

## 4. 仍未解释的部分 + 复现所需条件

### 4.1 未解释（全部为**未验证候选**，不得引用为结论）

| # | 未解问题 | 现状 |
|---|---|---|
| 1 | 为何恰好是**恒定 64 B** 且与帧长无关 | 候选：① TX 尾块按固定 64 B 单位取数，背压下少提交一个尾块；② 链路层 PAUSE（`0x8808`）在帧尾生效，MAC 提前终止当前帧；③ 发送侧主机 NIC 流控/PHY 状态导致 TX 供给不足。11-12 **未同时采板侧字节计数与背压计数**，三者无法区分 |

| 3 | PAUSE 帧（`0x8808`）是否参与 | PC1 侧扫描结果为 **0**；**PC2 侧待检** ⇒ 未定 |

### 4.2 复现所需条件（三条同时满足才有意义）

1. **物理板 A/B 换回 11-12 朝向**：PC1 连物理板 A、PC2 连物理板 B。
2. **PC 侧 NIC 流控 / PHY 状态可观测**：抓 `0x8808` PAUSE 帧 + 记录两侧 NIC 速率与流控设置（本项目已出现过 NIC 从 1 Gbps 掉到 100 Mbps 使 eth RX 全死的独立事件，见 `docs/M1_prj12_G0_B1D诊断执行报告_2026-11-19.md:96`–`:101`，可作混淆项参考）。
3. **两侧证据同时采**：发送板内部字节计数（`dbg_up_bytes` + 背压/溢出计数）与接收侧 pcap 帧数**同窗口对齐**，避免再产生"只有 pcap、没有板内计数"的单边证据（11-12 正是此状态）。

## 5. 对后续的判据约束

| 项 | 约束 |
|---|---|
| 满额判据 | A→B / B→A **一律**用 pcap 字节级 `cap == IP.len + 14`（len=100 → 142）。**只看帧数不算通过** |
| 双向独立 | A→B 与 B→A 各自单独判；一侧满额**不得**推定另一侧 |
| B1D 计数口径 | `dbg_up_bytes` = **线上帧 + 8 B 前导 + 4 B FCS**。len=100 → **154**（不是 142）；1200 → 1254；1472 → 1526 |
| 大跑计数 | `dbg_up_bytes` 是 16 位计数，**大跑会回绕** ⇒ 以 pcap 帧数判，计数器只做差分/自洽校验 |
| 形态区分 | 「每帧短 64 B」与「整帧丢失」是两种形态：`rtl/frame_mem_if.v:334` 的 `u_buf_drop` 表现为**整帧少**，不得记作 −64 B |
| 跨重烧 | 重烧会清零计数，**不得跨重烧做差分**（见 `docs/M1_prj12_G0_B1D诊断执行报告_2026-11-19.md:120`–`:121`） |

## 6. 复现入口（若再出现，按此跑）

1. **同参数 1 ms 六尺寸复跑**：A→B、B→A 各一轮（6×20 = 120 帧/方向），与 11-19 复测参数一致，便于直接对照。
2. **双向对角**：A→B 与 B→A 各跑一轮，**按物理板编号记录朝向**（不是按 PC 编号）。
3. **记录每台机器所连板的板面编号**：两块板 JTAG 序列号**同为 `210512180081`**，**不能靠序列号区分**，只能靠板面标签/资产号登记。
4. **判据**：`cap == IP.len + 14`，全帧满额才算过；**任一帧短 64 B 即重新立项**，不再沿用 11-12 的"B1 回归"标签。
5. **证据三件套**：双侧 pcap + 发送板内部计数 + 两侧 NIC 速率/流控记录，缺一项不判。
