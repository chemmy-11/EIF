## 2. B1 补丁本体（已核到行，用于定位 R2）

补丁：`out/evidence_2026-11-07_dma_stall/patches/B1_reset_pairing.patch`（6,162 B）。
**B1 提交 `9c04c66` 只改了 4 个文件**（2 个 RTL + 1 patch + 1 md），**没有动 XDC/构建脚本/时钟约束**
⇒ 硬件层唯一变量就是下面的 RTL 差异。

**2.1 `aurora_mem_bridge.v:259-265`（新增 ui 域镜像复位）**

```verilog
reg [3:0] arst_ui_pipe;
always @(posedge ui_clk or negedge ui_rst_n)
    if (!ui_rst_n) arst_ui_pipe <= 4'hF;
    else           arst_ui_pipe <= {arst_ui_pipe[2:0], aurora_rst};
wire aurora_rst_ui = |arst_ui_pipe;              // 展宽 ≈4 ui_clk
wire ui_link_rst_n = ui_rst_n & ~aurora_rst_ui;
```

`aurora_mem_bridge.v:216`：`wire aurora_rst = ~sys_rst_n | ~link_ok;`（`link_ok = channel_up`）
`aurora_mem_bridge.v:845 / :1003`：`frame_mem_if` 的 `.user_rst_n(~aurora_rst)`

> 注意：`aurora_rst` 是 **user_clk 域**信号，却被上面 `always @(posedge ui_clk)` 直接采样（未加 2FF 同步）。
> 用户在 ui 域看到的是一次"异步降 + 4 拍延迟"，释放时刻相对 user 侧是**不确定的**（取决于 CDC 相位）。
> 这一点对 R2 很关键：**释放沿的相对先后不确定 ⇒ 指针基准偏移量可能不确定，但一旦偏移就恒定**。

**2.2 `frame_mem_if.v` 五个 async_fifo 的"另一侧"复位改为 `ui_link_rst_n`**

| FIFO | DW/AW | 被改端 | 原接 | 现接 |
|---|---|---|---|---|
| `u_wr_bytes` | 8 / BF_AW | `rd_rst_n` | `ui_rst_n` | `ui_link_rst_n` |
| `u_wr_desc` | 16 / 3 | `rd_rst_n` | `ui_rst_n` | `ui_link_rst_n` |
| `u_rd_cmd` | 9 / 2 | `rd_rst_n` | `ui_rst_n` | `ui_link_rst_n` |
| `u_rd_bytes` | 8 / BF_AW | `wr_rst_n` | `ui_rst_n` | `ui_link_rst_n` |
| `u_rd_desc` | 25 / 2 | `wr_rst_n` | `ui_rst_n` | `ui_link_rst_n` |

## 3. R2 的根因假设（按可判别性排序，**已更新：H1 静态排除，并发现节奏混淆**）

### 3.0 ★ 新发现：11-06 的"基线正确"是 **20 ms 节奏**测的，今天 −64 全是 1 ms/0 ms

从 11-06 归档里那 20 帧的**到达时间戳**反推（`pc2_issue/comment_6682320881_20261106_180558.txt`）：

```
t=1793958627.565834 (seq0)
t=1793958627.586163 (seq1)   Δ=20.33 ms
t=1793958627.606745 (seq2)   Δ=20.58 ms
... 全程 ≈20.5 ms/帧
```

⇒ **11-06 的 A→B 20/20、`len=100` 是在 `--interval-ms ≈20` 下取得的**；
而 2026-11-12 所有出现 −64 的轮次是 `--interval-ms 1.0`（17:50 轮）或 `0`（17:12 轮）。

**结论：此前"基线 vs B1"的对照被节奏差异污染（约 20 倍）。**
所以 "R2 由 B1 引出" **不能成立为结论**——位流和节奏是两个同时变化的变量，而归档里没有
"基线 + 1 ms" 或 "B1 + 20 ms" 的数据。

**下一步的优先任务是补齐这个 2×2 对照矩阵**（离线做不了，但可以先算出最省板时的测法）：

| | 20 ms | 1 ms |
|---|---|---|
| 基线 `C856BA83` | ✅ 已有（11-06，`len=100` 正确） | ❌ **缺** |
| B1 `E9BE2B14` | ❌ **缺** | ✅ 已有（→ `len=36`） |

任补一格即可定案；两格补齐可完全分离位流与节奏。

### 3.1 ~~H1 单边复位 ⇒ 指针基准偏移 ⇒ `rb_level` 高估~~ **【静态排除】**

`async_fifo.v:93-99`：读侧复位时 `rd_bin / rd_gray / wr_gray_s1 / wr_gray_s2` **全部清零**。
- 对 `u_rd_bytes`（写=ui / 读=user）：链路恢复时 **user（读）侧先释放**，此时
  `rd_bin=0` 且 `wr_gray_s2=0` ⇒ `rd_level = 0`（判空，不发射）；ui（写）侧晚 ≈4 ui_clk 释放后从 0 开始写。
  ⇒ **不存在偏移**。
- 对 `u_wr_bytes`（写=user / 读=ui）：先释放的写侧从 0 计数，后释放的读侧重新同步写指针。
  ⇒ 同样**不存在偏移**。

⇒ B1 的复位配对不对产生"恒定水位偏移"，`frame_mem_if.v:417` 的 `rb_level >= rd_len_o` 判据在 B1 下依然成立。

### 3.2 ~~H3 pack/出口按 64 B 截断~~ **【静态排除】**

- 读路径对长度忠实：`axi4_master_bridge.v:1013` 末拍 `r_nbytes = r_len[5:0]`（`0→64`），
  `:1006` `m_axi_arlen = r_beats-1`，`:250` `len_beats_tab = (len+63)>>6` ⇒ 不会少读一拍。
- 出口 mux 干净：`aurora_mem_bridge.v:1325-1328`，`rgmii_txd_o = cmd_takeover ? cmd_resp_txd : pump_rev_data`，
  而 `cmd_takeover` 只服务 **W5 命令通道（端口 1235）**；本轮流量走 1234 ⇒ 不经过该 mux 的接管分支。
  （该 mux 的已知残余风险见 `:1321-1323`，与本现象无关。）

### 3.3 剩余候选（下一步查这两条）

**H2-a：入口帧边界少算 64 B** —— `len_tab` 存的是 `frame_mem_if` push 的字节数，
而 push 的字节数由 **SOF→EOF 之间的字节**决定（`frame_fifo_pump` + `rgmii_rx_fix2`）。
若 RGMII RX 的 DDR 采样/延迟导致 **EOF 提前**，则每帧恒定少一段。
→ 离线可做：`frame_fifo_pump` + `rgmii_rx_fix2` 的定向 TB（给定固定字节流与已知 EOF 时刻，测 push 计数）。

**H2-b：`wr_commit_len` 统计口径** —— `axi4_master_bridge.v:249` `len_tab[slot] <= wr_commit_len`。
若 `wr_commit_len` 把"最后 64 B 未**提交**"当成完成（例如 `wf_level >= wd_len` 的边界比较差一拍），
则表里少 64。→ 离线可做：静态核对 `:742` `wf_level >= wd_len[12:0]` 的比较位宽与语义。

> 注意 `:742` 的比较用了 `wd_len[12:0]`（13 位）而 `wd_len` 是 16 位 —— **位宽截断**，值得单独核。

### 3.4 ★ O2 的强推论：缺口在「unpack → mem2 的 push 计数」，不在读路径、不在出口、不在 B1 的 FIFO 复位

**推导链（每步带行号）**

1. `axi4_master_bridge.v:836` `wr_commit_len <= wd_len;`
2. `:249` `len_tab[wr_commit_slot] <= wr_commit_len;` ⇒ **`len_tab` = 描述符长度**
3. `:1095-1096` `r_len <= len_tab[p_eff]; r_beats <= len_beats_tab[p_eff];`
   `:1013` 末拍 `r_nbytes = r_len[5:0]`、`:1006` `m_axi_arlen = r_beats-1`
   ⇒ **读侧发出的字节数严格等于 `len_tab`**（不会多也不会少）
4. PC2 实测：帧的 **IP 头里 `ip_total_len` 仍是原始值（1228）**，而实际只到 1164
   ⇒ 发出去的帧长就是 `len_tab`，`len_tab = 1164 = 1228 − 64`
5. `len_tab` 的上游是 `frame_mem_if` 的 push 计数（`n_push` / `n_push_r`），
   而对 **A→B** 而言，写这个 frame_mem_if 的是 **板 B 的 `u_mem2`**，其输入来自 **`axis_word_unpack`**
   （`up_frames` 侧）

**⇒ 结论：`unpack` 为这一帧吐出的字节数比 IP 头声明的少 64。**
把范围从"读引擎/AXI/出口 mux"整体排除，落到 `axis_word_unpack.v` 的 keep/字节计数上。

**为什么这条能解释"只有 A→B 坏"**：两个方向的 unpack 是**不同的板、不同实例**
（A→B 用板 B 的 unpack；B→A 用板 A 的 unpack），所以只要两侧输入数据的**字对齐**不同，
同一个 RTL 就可以表现为一侧正确、一侧恒定偏移。

**下一步要看的具体代码**

- `axis_word_unpack.v:143` `nf_n <= popcnt8(wf_keep[wf_rd[AW-1:0]]);` —— 每个 64-bit 字有效字节数
- `:102` `word_done = (cur_n == 4'd0) | ((byte_i+1) == cur_n)`
- `:178` `o_byte_cnt <= o_byte_cnt + 1` —— 与 `o_frame_cnt` 的配合
- `axis_word_pack.v:85` `tail_keep_w = 8'hFF << miss`（`miss = 8 − asm_cnt`）—— 末字 keep 的构造
- **`o_stall_cnt` 是设计自带的金丝雀（`axis_word_unpack.v:26` 注释"整帧转发后正常应恒为 0"）
  —— 但 B1 的 53 条探针里没有它，**这是 B1D 诊断位流最该补的探针**。

## 5. 为什么先离线（而不是先上板复测）

1. **两板位流现在不一致**（A=基线 `C856BA83`、B=B1 `E9BE2B14`），上板读数一律不可用；
2. PC2 侧**没有基线件**，"两板同基线"对照做不了；要等 B2 产出后**一次把两板都换成 B2**，才有一个干净的同版本窗口；
3. `−64` 是**确定性偏移**（不是偶发），这类缺陷最适合在 TB 里构造复位偏斜直接复现，比上板试错快一个数量级。

```text

④ 若 ①② 通过 → 才进入 A1 的六尺寸 + 10 MiB + 5 轮 + 同时双向
```

- 本轮**不动板卡**；不重烧、不占 hw_server；
