# prj9 / prj10 / prj11 复现指南

> 两块工程共用一个板卡环境：正点原子 KU060（`xcku060-ffva1156-2-i`）+ 单板双笼光回环。
> **prj9 = 以太网 ↔ Aurora 光回环**（无内存）；**prj10 = 在光口两侧各插一级 DDR4**（内存进环路）。

---

## 共用前提（两个工程都一样）

| 项 | 值 |
|---|---|
| 板卡 IP | `192.168.1.10` |
| PC 网卡 | `192.168.1.102/24`（网卡名「以太网」） |
| 数据端口 | UDP **1234**（PC 侧绑 1234） |
| 命令端口 | UDP **1235**（仅 prj10；广播 `192.168.1.255:1235`） |
| 工具链 | Vivado **2023.1**（`D:\Xilinx\Vivado\2023.1\bin`） |
| 控制台编码 | 跑任何 Python 前先 `$env:PYTHONUTF8 = 1`（否则中文/对勾字符会崩） |

**开机三件事**：① 板卡上电并接好光纤回环；② 烧一次位流（**JTAG 烧录是易失的，每次断电都要重烧**）；
③ `ping 192.168.1.10` 通。

## ⚠️ 三个真实踩过的坑（复现前先看，能省几小时）

| # | 现象 | 真因 | 处置 |
|---|---|---|---|
| 1 | prj10 命令无应答 / 单播丢 14/16 | **RND 模式下板子无法应答 ARP**（应答帧要经「内存→泵B」，而 RND 不自动读）⇒ PC 邻居表老化成 `Unreachable`。**不是板卡故障，也不是 WLAN 抢路由** | 测试引擎已自愈（每轮先 `SET_MODE(SEQ)` 预热 ARP 再切 RND）；也可加静态邻居项 |
| 2 | 同时接了 WLAN 时流量走错网卡 | Windows 多网卡路由/源地址选择 | 用 `--pc-ip 192.168.1.102`（prj10 已内置）或临时断 WLAN |
| 3 | 位流/探针不配对，ILA 抓不到信号 | 位流与 `.ltx` 必须**同批产出** | 用指南里的 SHA256 闸门核对后再烧 |
| 4 | 测「板卡速率上限」得到的结果其实是 PC 的节拍 | **报价没盖过被测上限**：`--pace-us 20` 时 PC 最多只能报 50k fps，把 128B 档的板卡真实上限（≥117k）遮住，线性拟合便把「PC 节拍」拟成了「板卡固定开销」（实测曾据此走错方向做了无效修复）| **测上限固定用 `--pace-us 5`**，并先确认「PC 发出速率」显著高于预期上限 |
| 6 | **prj11 上电后 ping 不通 / 计数不动** | R2 设计 `g_dma_mode` 默认 0：无读/写服务 | 上电后先发一次 `'d'`（toggle，用 `'U'` 确认 mode=1），再 ping |
| 7 | **prj11 J3 报 `wr+255`/收帧停摆** | J3 对板卡起始态（残留槽/backlog）敏感 | **重烧后再跑**，不重试（脚本会自动 'S'+'d'）|
| 5 | 跑完 RND 用例后，后续依赖回显的测试「收到 0 片」 | RND 模式桥① 不自动读，回显路径本就不通 | 跑 RND 用例前后都 `SET_MODE(SEQ)`（本轮已给 `deadlock_regress.py` 补上收尾恢复）|
