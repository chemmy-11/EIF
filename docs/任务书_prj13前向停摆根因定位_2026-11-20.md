## 0. 一句话

prj13 P2 双板在**一次 link-down→up 之后**，前向通路永久停摆（帧进得去、出不来），只有整板重配置能恢复。
但这个"停摆"的**卡点位置从未被测过**——已有的差分链只读了两端。本任务要求把它定位到**具体模块与状态**，并判定"这是状态残留问题还是启动时序问题"。

---

- **不需要改 RTL、不需要重建位流**：本文 §4 列出的探针**已经在现网 A 版位流 `3a8b6300` 里**（`probes_p2_b30c3903.ltx`，5 个 ILA 核，53 个探针）。抓取即可定位。

| 23:12 | **光纤断开**下重烧 A → 再插回 | `ch_up=1 / aurora_rst=0` 但 `pfwd_wr=3 / pk_frames=0` ❌ | `ila/reburn_fiberout_A.csv`（断纤态）、`ila/after_replug_3f_A.csv`（插回后） |

### 2.2 关键反差（本任务的出发点）

**23:08 与 23:12 都是"重烧 A 之后"，但结果相反。** 唯一已知差异：

- 23:08：**烧录时光纤在位**（链路已建立）
- 23:12：**烧录时光纤断开**（烧完再插回）

这条反差很要紧：**如果是"状态残留/泄漏"类问题，一次完整重配置就该清干净**。23:12 恰恰是全新配置之后卡死的 ⇒ 更指向**启动时序**（配置时链路不在场 → 链路后到时某些状态没有正确初始化），而不是残留。

> ⚠️ 注意：这是**推断，不是结论**。它需要 §7 的 E1/E2 复现才能升级。

### 2.3 已排除的方向

- **D1「RGMII TX 三路 mux 的 `stack_takeover` 锁存卡死」已被实测推翻**：`u_ila_7` 抓取显示 `stack_takeover` 整窗恒 0，而 `pump_rev_en` 有约 142 拍脉冲 ⇒ mux 没卡、泵确实在发。见 V4 报告 §11.2。
- 该结论来自 **B 侧（收帧侧）** 位流；A 侧本题不涉及 mux。

### 2.4 停摆的判别链是**设计好可对账**的

`rtl/aurora_mem_bridge.v:1447-1449` 注释原文：

```
差分链(插入内存桥后): pfwd_wr → [桥 u_wr_frame → u_rd_frame] → pk_frames
                      → echo_b_rx → echo_b_tx → up_frames → prev_wr
```

**但 23:12 那次只读了链的两端**（`pfwd_wr` 与 `pk_frames`），中间段一个都没读 —— 这就是"根因不清楚"的直接原因。

## 5. 判据树（**一次 `u_ila_3` 抓取即可二分**）

抓取失败态的 `u_ila_3`，按 `dbg_mem_wr_frm` / `dbg_mem_rd_frm` / `dbg_mem_ost` 的静止值判：

| 观测 | 卡点 | 下一步 |
|---|---|---|
| `mem_wr_frm = 0`（且 `pfwd_wr=3`） | **写侧没落 DDR**：pump A 写了、frame_mem 没接住 | 查 pump A 读侧与 `wr_hold`/`ub_full` |
| `mem_wr_frm = 3`、`mem_rd_frm = 0` | **读侧不出**：DDR 里有帧、读引擎不取 | 查 `mem_rd_req` 触发条件与 `outstanding` 是否真的非 0 |
| `mem_rd_frm > 0`、`pk_frames = 0` | **pack/Aurora TX 侧**：数据取出来了但没打包发送 | 查 `u_pack` 与 Aurora TX 握手 |
| `mem_len_err` 或 `mem_stall` 在涨 | **帧边界/描述符异常** | 查帧长写入口径与 `MAX_LEN` |
| `dbg_calib = 0` | **MIG 未校准** | 不是本问题，单列 |
| `mem_ost` 很大（接近 256） | 槽位泄漏，`wr_hold` 将被钉死 | 与"残留"假设一致 |

> 这张表就是本任务的核心：**任何一格命中都能把"根因不清"变成"根因清楚"**。

## 6. 竞争假设与各自预测（请逐个证实/否证，不要只挑一个）

| # | 假设 | 预测的可观测差异 | 现状 |
|---|---|---|---|
| **H1** | 状态残留/泄漏（槽表、outstanding、FSM 未随链路复位重建） | 不重配置就永久卡死；**且重配置后必然恢复** | **23:12 重配置后仍卡死 ⇒ 单独 H1 解释不了** |
| **H2** | 启动时序（配置时链路不在场 → 链路后到 → 某状态未初始化/未对齐） | 断纤烧录→插回 卡死；在位烧录 正常，**可重复** | 23:08 vs 23:12 与预测一致，但**样本量 n=1，未复现** |
| **H3** | 写侧未落 DDR | `mem_wr_frm` 停在 0 | 未测 |
| **H4** | 读侧不出 | `mem_wr_frm>0 / mem_rd_frm=0` | 未测 |
| **H5** | 链路"半通"（`ch_up=1` 但数据面不通） | A 侧 `mem_rd_frm` 与 `pk_frames` 都涨，但 **B 侧 `up_frames` 不涨** | 未测（23:12 未同时抓 B 侧） |

H3/H4 与 H1/H2 不互斥：**H1/H2 是"为什么会坏"，H3/H4 是"坏在哪"**。最终结论应当给出一对（原因 + 位置）。

## 7. 最小实验集

> 全部只读抓取，不改 RTL、不重建位流。单次上板窗口可完成。

| # | 实验 | 目的 | 次数 |
|---|---|---|---|
| **E1** | **光纤断开**状态下烧 A → 插回光纤 → 发 3 帧（run id 固定）→ 抓 `u_ila_3` + `u_ila_6`（B 侧同时抓 `u_ila_6` 看 `up_frames`） | 复现 23:12；拿到中间段，判 H3/H4 | **n≥3** |
| **E2** | **光纤在位**状态下烧 A → 发 3 帧 → 抓同样两组 | 对照臂，判 H2 | **n≥3** |
| **E3** | 只在 E1 稳定复现时做：断纤烧录 → 插回 → **不发帧**等 10 s → 再发 3 帧 | 区分"需要时间"与"需要帧触发" | n≥1 |
| **E4** | 只在 E1 稳定复现时做：断纤烧录 → 插回 → 只重载软核（`dow`+`d`）→ 发 3 帧 | 检验"是否必须整板重配置" | n≥1 |

**判据**：E1/E2 各 3 次结果一致（全卡 / 全通）才算复现成立；否则 H2 不成立，转向 H3/H4 的现场取证。

**注意事项**：
- 烧录时必须保证 **Vivado 全局串行**（同一时刻只有一个 Vivado）。
- E1/E2 的位流必须是**同一个文件**（`3a8b6300`），否则对照失效；记录 bit 与 ltx 的 sha256。
- B 侧（PC2 板）当前是 B3 `edaf06c9`；若需重新烧 B，注意**任一侧重烧都会让对侧闪断**——这本身可能干扰实验，需在记录里注明。

## 10. 提出方目前的倾向（**仅供参考，可推翻**）

1. **H2（启动时序）最值得先查**：H1 解释不了 23:12 这个"全新配置后仍卡死"的事实。
2. 但**不要因此在 E1 之前下结论**——n=1 的反差不足以定级，必须先复现。
3. 若 E1 稳定复现且 §5 判据树指向"读侧不出"（`mem_wr_frm=3 / mem_rd_frm=0`），那 H1 会以"outstanding 与槽表失配"的形态复活——**注意这与"命令永久为空"不是同一个命题**，别混。
4. 认为**最可能的最终答案是"原因 + 位置"这一对**，而非单一原因。

## 11. 为什么建议交给已经做过上一份决策的那一方

不是能力问题，是**校准**问题。上一份《FIFO 复位补丁去留》里有三处表现出好的判断纪律：

- 把结论明确分档为"机制确定 / L1 假设 / 待测"，并在同一段里写明"**决定 C 不依赖这个归因**"；
- **主动否决了提出方（PC1）的归因**，并给出可复核理由（`mem_rd_req` 会重试、`uc_wr_en` 仍可写）；
- 自己挖出了 `silent.neg` 那条关键负对照（"不锁死但提交垃圾帧，只有内容判据能抓"）。

根因定位最怕的就是"把假设写成结论"。本任务的核心判据树（§5）已经把"哪一格命中就是哪一个卡点"固定下来，**照表读数即可，不需要猜**。
