# GSnFPipe 方案对齐包 — 说明与 agent 使用契约

## 0. 本包是什么 / 不是什么

**是**：对导师 2026-10-22 下发的《GSnFPipe FPGA+PP 联合实验》三份 v1.0 文档（下称"方案文档"）做**需求级对齐**的输入包。它只回答四件事：

1. 方案文档中的**事实性假设**，与本项目**可复核的工程事实**是否一致（`02`）；
2. 方案文档在**硬件层**缺少/歧义/冲突的信息是什么（`03`，本包新增内容最多的一节）；
3. 哪些问题**必须由导师或项目负责人拍板**、各选项的代价与阻塞范围（`04`）；
4. 上述判断所依据的 **AMD 官方文档原文**（`05`）。

**不是**：实施方案、工期承诺、RTL/软件设计文档、实验数据。所有 `Q-` 未决之前，不进入对应里程碑的开发；本包不替代 `protocol_v1`。

**信息基座声明**：导师侧目前掌握的工程事实**仅有**《导览_cross_已完成工作说明_2026-10-22》（下称"导览"）。本包正文中的每条工程事实都**自包含陈述**，附证据标签与可复核动作，不依赖读者访问本项目内部文档。内部路径仅作溯源，不作为理解前提。

## 1. ID 与证据制度

### 1.1 ID 命名（全包稳定，跨文件引用）

| 前缀 | 含义 | 出现在 |
|---|---|---|
| `F-xx` | 事实（可复核的陈述） | `01` |
| `U-xx` | 未确认项（事实缺位） | `01` |
| `A-xx` | 方案假设（导师文档中的前提） | `02` |
| `D-xx` | 硬件缺口/歧义/冲突（对导师文档的补充项） | `03` |
| `Q-xx` | 待决问题（需人拍板） | `04` |
| `R-xx` | AMD 官方文档依据 | `05` |
| `M1`–`M4` | 方案文档定义的里程碑 | `02`/`04` |

### 1.2 证据标签（每条 `F-` 必带主标签；可附一个佐证标签）

| 标签 | 定义 | 对应 AGENTS.md §6a 等级 | 使用规则 |
|---|---|---|---|
| `[实测]` | 本机/本板直接观测（ping、哈希、ILA、串口输出、位流哈希） | L3（板证实）/ L4（定案） | 可直接作为验收证据 |
| `[工程]` | 工程文件、IP 参数、XDC、Tcl、寄存器表、ELF/XSA 哈希 | L2–L3 | 可作设计输入；引脚/行为仍以实测为准 |
| `[手册]` | 板卡手册、厂商资料 | L3（知识轴） | 只作方法论与默认值参考；与本板实测冲突时以实测为准 |
| `[官方]` | AMD PG/UG/SP/Answer Record | 知识轴最高权威 | 必须给 URL + 本工程落点（见 `05`） |
| `[确认]` | 项目负责人已确认的**硬事实**，尚未实测（如两板同款同配置） | L2（事实确认） | 可作设计与排期输入；仍须以 `hardware_inventory`/实测留证，不能单独充当 M1 证据 |
| `[口述]` | 口头/聊天确认，未书面化 | L1（假说） | **不得作为 M1 判据**；必须转写进 `hardware_inventory` 并由双方确认 |
| `[推断]` | 由上述事实推导，无直接观测 | L1（假说） | 必须写推导式；不得写成"已确认" |
| `[未知]` | 无证据 | L0 | 只能进 `U-`，不得作为设计输入 |

### 1.3 冲突裁决顺序（本包强制）

1. **工程事实/判据轴**：`[实测]` > `[工程]` > `[确认]` > `[手册]` > `[推断]`；
2. **知识/工具语义轴**：AMD 官方文档最高（IP 参数含义、协议规则、时序方法学）；
3. 两轴冲突时：**不得二选一**，必须新建 `D-` 或 `Q-`，并列两栏证据（AGENTS.md §二「两轴采信」）。
4. 同一事实出现两个来源时，保留**更晚且有实测证据**者，旧来源标"已被取代"，不得删除（可追溯）。

## 2. Agent 使用契约（导师侧审阅 agent 必读）

> 本包按"可被 agent 审计"设计。请按以下 8 条使用；违反任一条会使结论不可追溯。

- **G1 三分法**：`F/R` 是输入事实；`A` 是待验证前提；`Q` 是未决决策（`U/D` 为待补事实与缺口）。**不得**把 `A` 当 `F` 用，**不得**在 `Q` 未决时默认任一选项。
- **G2 引用格式**：引用本包内容必须带 ID（如 `F-17`、`Q-05`）；引用方案文档必须带"文档名 + 章节号"；引用官方文档必须带 URL。**不引用无 ID 的口头信息**。
- **G3 禁止外推**：不得由已有 `F-` 推出未列出的参数（如"既然 10G 光口，就能跑 10G 端到端"）。需要新参数时新建 `Q-`，不得在正文中静默假设。
- **G4 数值口径**：任何数字必须带单位与口径（`Mbps` vs `MB/s`、`line rate` vs `user clock`、`payload` vs `frame`、`bit` vs `byte`）。本包 `F-` 已标口径，引用时不得省略。
- **G5 统计口径**：`[实测]` 的"0 error"只表示**该批次未观察到**，不得写成"无错误/绝对可靠"（方案文档 §6.3 同款要求）。
- **G6 物理动作**：涉及上电、插拔光纤/模块、烧录位流、JTAG 复位的动作，必须人工在场确认；agent 不得自行下发。
- **G7 版本纪律**：本包引用方案文档 **v1.0（2026-10-22）**。方案文档升版后，`A-`/`Q-` 必须重新核对，不得沿用旧 ID 的结论。
- **G8 变更留痕**：本包任何修改必须改 `updated` 与"变更记录"，新增条目一律**追加新 ID**，不得复用已删除 ID。

## 4. 结论摘要（一屏）

1. **方案文档对工程现状的引用是准确的**：路线 A 纯硬件 ≈969 Mbps、路线 B 软核逐帧 ≈23 Mbps、256 槽 × 4 KB、单帧 1466 B、Aurora 10G 单通道、跨时钟整帧搬运、DDR4 4 GB 已校准——这些与导览一致（`02` 的 ✅ 行）。
2. **真正的缺口不在"他理解错了"，而在"导览没写、方案却当作已有条件"**：第二块板虽为**同款同配置（硬事实）**，但从未参与任何实验（`U-01`）、每板第二路千兆 GE2 从未 bring-up（`F-17`）、跨板 Aurora 从未连过（`F-04`）、任务级 DDR 缓存/门控/日志/命令执行器全部是新建（`A-08`/`D-09`）。
3. **三个算术必须在对齐阶段解决**：
   - 现有队列 **256 × 4 KiB = 1 MiB**，而方案自己的算例（65,536 B × M=8 × 正反双向）**正好 1 MiB**，M3 的 hold 无余量（`D-10`）；
   - Aurora 有效 ≈9.7 Gbps vs GE1 有效 ≈0.95 Gbps，**约 10×速率差**，且 Aurora RX **无 tready**，只能端到端窗口或丢弃（`D-11`、`R-06`）；
   - 串口 9600 = **960 B/s**，事件日志必须走 GE1/UDP（`D-08`、`R-09`）。
4. **一处表述有歧义（不是事实错误）**：方案 §0.3 "目前仅有一条真实 FPGA—FPGA 光段"——导师 2026-10-23 澄清其意为**计划实现一条**（范围），不是"已有一条"。现状是 **0 条跨板光段**（现有全部为单板双笼回环，`F-04`）。建议方案措辞改为"计划实现一条"，并把"现状 0 条"作为 A1 的起点写清。
5. **可靠性分工与官方口径一致**：Aurora 协议无重传、CRC 是 IP 自用，端到端 ACK/重传只能由 B 组协议层承担（`R-05`）；这支持方案 §4.3，但 FPGA 侧背压策略仍需 `Q-12` 定案。
