## 二、DMA 读路径设计（下一轮实施，先记录决策以免走错）

### 决策 1 · 时钟域（最容易踩错的一处）

`axi_dma` 的 AXI4 **存储映射口**有独立时钟：`m_axi_mm2s_aclk` / `m_axi_s2mm_aclk`，
可与控制口 `aclk` 不同。故：

- 控制口 `aclk` = **100 MHz**（BD 现有时钟，软核/寄存器侧）；
- `m_axi_mm2s_aclk` = **ui_clk 300 MHz**（与 MIG 同域，直接进仲裁器 S02）；
- MM2S 的 **AXI4-Stream 输出**（`m_axis_mm2s_aclk`）同样在 300 MHz ⇒ shim 直接在 ui 域
  把 512 bit 流拆成字节，写入 `frame_mem_if` **既有的 ui→user 读字节 async FIFO**
  —— **不需要新增任何 CDC**（该 FIFO 本来就是干这个的）。

带宽核算：512 bit × 100 MHz = 6.4 GB/s ≫ 线速 121 MB/s，所以 DMA 的 M_AXI 即使挂在
100 MHz 也不会成为瓶颈；但**与 MIG 同域**可以省掉一次 AXI 时钟转换（也避免跨域 AXI 的
异步 FIFO 面积/时序代价）。⇒ 采用 300 MHz。

### 决策 2 · 描述符策略（SEQ 与 RND 的实时性不同）

| 模式 | 触发源 | 速率 | 策略 |
|---|---|---|---|
| **SEQ**（写进槽即自动读回，回显路径） | 硬件（每帧写提交后） | **线速 ~82k fps（12.3 µs/帧）** | 软件不可及 ⇒ 必须硬件驱动：**(a) SG + 循环描述符环**（置 `c_include_sg=1`，描述符放 BRAM，环回扫 0..255 槽）；或 **(b) 硬件"描述符写入器"**（direct-register 模式：小 FSM 观察"有帧可读"→ 写 SA/LENGTH → 置 start → 等 Idle） |
| **RND**（软核指定槽读一次） | 软核命令 | 毫秒级（B2 实测 1–4 ms/次） | 软件逐笔写描述符即可 |

**推荐 (a) SG 循环环**：SEQ 路径完全硬件节拍、无 CPU 参与；RND 时软核插一笔描述符
（需短暂接管环）。代价：要开 SG（描述符取指走 AXI，需给 DMA 描述符存储 + 地址映射），
B0 记录里参考 BD 用的是 `c_include_sg=0`，故这部分是**新的面积与配置风险点**。
**(b) 是更保守的备选**：不动 SG，只加一个小 FSM；缺点是每笔要等 DMA 回 Idle，节拍紧但可算
（12.3 µs 预算 vs 约 1 µs 编程开销）。

### 决策 3 · 地址与长度映射（B3 草案「写槽规则逐字等价」落点）

- 桥② 槽区基址 `SLOT_BASE = 0x0020_0000`，槽步长 **4 KB**（`SLOT_BASE + {slot,12'b0}`）；
  DMA 的 `SA = SLOT_BASE + slot × 4096`。
- **长度不是 64 的整数倍**（帧长各异）：MM2S 的最后一拍用 **TKEEP** 标记有效字节 ⇒
  shim 必须**按 TKEEP 截断字节数**（不能只数拍数），否则读出的帧会拖尾。
- 读描述符（`rd_wr_data = {1'b0, len[15:0], slot[7:0]}`）由 shim 在 `TLAST` 拍生成，
  与桥② 现有格式**逐位一致**（改完 `frame_mem_if` 下游零改动）。

### 决策 4 · 分步实施（每步独立可验证，避免一次动太大）

| 步 | 内容 | 判据 |
|---|---|---|
| **B3-1a** | BD 加 `axi_dma`（512b, MM2S），控制口 100M / MM2S 口 ui_clk；M_AXI_MM2S 引出接仲裁器 S02；**先只做"存在性 + 单笔搬运冒烟"**（MM2S 从某槽读 → 流 → BD 内 BRAM，软件回读比对） | 板上：单笔搬运字节一致；W2/W4 回归不受影响 |
| **B3-1b** | 加 `dma_rd_shim.v`（512b 流 → 字节 FIFO + 读描述符，按 TKEEP/TLAST）；SEQ 路径切 DMA（决策 2a/2b 择一）；RND 暂留旧桥（仲裁器 S01/S02 并存） | 四档逐字节 PASS（SEQ 回显全链） |
| **B3-1c** | RND 也走 DMA 描述符；退役桥② 的读引擎 | J3/J3′ + 负向 A/B 复跑 PASS |

### 教训（坑账本候选）

### 根因：axi_dma MM2S 512b 数据通道的确定性映射（非故障）

用 512B 特征帧（byte[i]=(i>>2)&0xff，每 64B 块低 32 位自编码块号）做地址偏移扫描
+ 两次独立 seq 帧预测验证，锁定规律：

1. **DMA 读地址 X，返回的流 = MIG 块 (X−64) 的内容**——IP 内部 512b 装配
   有一拍/64B 的偏移（SA=槽+0x40 时流恰好是槽基址块的内容）；
2. **sink q1（首拍低 32 位）= 该块字节 14..17 的 LE 值**——512b 字内 lane 有
   交织（首次特征帧解读误判为 12,13,16,17 是因为特征图案撞值，seq 帧纠正为
   连续 4 字节 14..17；两次预测 0x5e3914ef / 0x7c57320d / 0x9a75502b 全中）。

**为什么不是缺陷**：桥① 读写走同一 MIG 从口且写读对称（写 byte i→lane perm(i)，
读 lane perm(i)→byte i），自洽；四档 300 帧逐字节全对就是证明。DMA 直接消费
原始 lane 顺序，看到的是交织后的视图。**该映射确定性可复现**，冒烟口径按它校正
（'D' 的 SA 加 0x40 预补偿，q1 判据 = 载荷字节 14..17 的预测值）。B3-1b shim
接入时在字节流重排处一并去交织（或验证 SG/不同长度下映射是否一致）。

### 过程中第二发现：M01 Lite 读滞后恶化（坑 #39 升级）

- interconnect 扩 3 MI（NUM_MI 2→3）后，M01 读从"休眠边界后首笔陈旧"恶化为
  **每笔落后一笔**（JTAG 18 笔对照实证：读 N 返回事务 N−1 数据，与地址无关）；
- **0x2C 哑写疗法失效**；现行缓解 = `rd_reg()` 改双读（保留哑写冲刷 + 取第二笔），
  板上验证 sa/q0/q1/q2 全部新鲜；`dread()` 双读对 DMA 寄存器一直有效即此理。
- 根治（换互联结构 / ILA 挂 AR/R 取证）与 B3-2 合并排期。

## 三之五、B3-1b 离线：字节映射判决与 shim 对策（2026-10-14）

### 1) xsim 判决：axi_dma MM2S IP 本体是**线性透传**（推翻"IP 内部装配偏移"假说）

用**同一 XCI 生成的 IP 仿真网表** `mb_ctrl_axi_dma_0_0`（与板上位流同参数：
512b / direct / DRE=0 / SF=1）+ 线性寻址 AXI 从机（`byte(addr)=addr&0xFF`）跑
三例（`sim/dma_probe_tb.sv` + `run_dma_probe.bat`）：

| 例 | SA | AR 实测 | 首拍 |
|---|---|---|---|
| 1 | 0x0010_0040, LEN=64 | `addr=00100040 len=0 size=6 burst=1` | `40 41 …7f` = mem[SA..SA+63] **线性** |
| 2 | 0x0010_0100, LEN=128 | `addr=00100100 len=1` | mem[SA..] 线性 |
| 3 | 0x0010_0024（非对齐） | `addr=00100024 len=1` | `tk=fffffff000000000`（lanes 36..63 有效，**不左移**，靠 TKEEP 标注） |

结论：**IP 不改写 AR 地址、不打乱 R 数据、不对齐左移**——纯透传。故 §三之四
假说 1「IP 内部有一拍/64B 装配偏移」**不成立**；IP 对非对齐 SA 的正确行为是
"块对齐数据 + TKEEP 标注有效 lane"（例 3 实证）。

### 2) 板上证据重推导：是**纯 50 字节窗口平移**，不是拍内 lane 交织（修正 §三之四）

- **F1（桥侧）**：四档回显判据 `udp_verify_ddr.py` 用的是 `rx == p` **整串字节等值**
  （长度+位置严格），PASS ⇒ DDR 里 `mem[slot_base]` 就是帧字节 0（写读同址，自洽）。
- **F2（DMA 侧）**：DMA 读 SA 得到的数据 = `mem[SA−50 .. ]`，偏移**恒为 50**：

| 帧 | 槽 | 读 SA | q1 实测 | 独立复算 | 结论 |
|---|---|---|---|---|---|
| build_payload(70020,9,64) | 108 | base+0x40 | 0x401bf6d1 | `payload[i]=(i*37+(seq&0xFFFF)*131+63)&0xFF` → payload[14..17]=D1 F6 1B 40 | 偏移 50 |
| build_payload(70050,9,64) | 120 | base+0x40 | 0x9a75502b | payload[14..17]=2B 50 75 9A | 偏移 50 |
| 特征帧 byte[i]=(i>>2) | 111 | base+64/128/…/448（8 点） | 0x04040303 / 0x14141313 / … | feat[(SA-base)−50] 全中；偏移 51 会得 3,3,3,4 | 偏移 50 |

**关键判别**：观测到的是**载荷连续 4 字节**（payload[14][15][16][17]），说明是
**地址窗口整体前移 50 字节**，不是"块内 lane 重排"——重排不会得到连续载荷字节。
故 §三之四 中"512b 字内 lane 有交织 perm(i)"的推测**予以更正**：不存在 lane 交织。
（原判据 `q1=该块字节 14..17` 的"块"其实指同一偏移窗口，非 lane 交织。）

**AXI 自洽性一票定音**：对齐 SA 的 512b 拍数据**必须**等于 `mem[SA..SA+63]`
（块对齐硬约束）。F2 观测该拍低 4 字节 = 帧字节 14..17 ⇒ 帧字节 0 落在
`mem[SA−50+64]`。再看 F1：桥读"槽基址"得帧字节 0。两事实合一只能解释为
**帧在槽内落在 +50（DMA 视角）**。"读侧 −50"会破坏块对齐、与 AXI 矛盾，排除。

**机制定位（离线穷尽）**：IP（xsim 线性）✓ / 三主仲裁器 araddr 逐位（`M_AXI_MM2S_0_araddr[i]→c0_ddr4_s_axi_araddr[i]`，bits 5..31 全带 S02 臂）✓ /
MIG S_AXI（512b/araddr 32b，xci）✓ / 桥写 FSM（`w_bi<=0` lane0 → `slot_base+i`）✓ /
泵A（乒乓 FIFO 无前导）✓ / 顶层·BD 接线（`make_bd_intf_pins_external` 直连，1:1）✓
——**无一能产生算术 −50**。故 50 的真实侧别（读地址侧 vs 槽存储侧）**留待板上
AR/R 抓取定位**（B3-1b 重建时给 DMA 的 M_AXI 加 ILA 探针），但**对"按帧读回"
两端完全等价**（纯字节窗口平移），不影响本件对策。

### 3) 对策（已实现、已单元验证）：对齐读 + 帧首丢弃

`rtl/dma_rd_shim.v` 增 `parameter DROP_BYTES`（默认 0，保持既有回归不变）：

- **读配置**：`SA = SLOT_BASE`（**对齐**，避免非对齐突发）、`LEN = 帧长 + DROP_BYTES(50)`；
- **shim**：帧首丢弃 `DROP_BYTES` 个**有效（TKEEP=1）**字节后再压入字节流并计长，
  描述符 `len = 帧长`（已扣前导）；
- **等价性**：无论 50 在读地址侧还是槽存储侧，输出都正好是帧字节 0..len-1。

单元验证（`sim/shim_drop_tb.sv` + `run_shim_drop_tb.bat`）：

```
[D1] 200B 帧 + 50B 前导 -> 纯帧 200B ✓
[D2] 512B 帧 + 50B 前导 -> 纯帧 512B ✓
[D3]   1B 帧 + 50B 前导 -> 纯帧   1B ✓
[D4]  64B 帧 + 50B 前导 -> 纯帧  64B ✓     SHIM_DROP_TB: PASS (0 errors)
```

既有单元回归 `shim_tb`（S1–S4 + NEG 无 TLAST）**0 错复跑 PASS**（DROP 默认 0，无回归）。
前导填 0xEE 且与帧内容不同，漏丢必被抓；D3/D4 覆盖"前导+帧"同处首拍内的边界。

### 4) 集成口径（B3-1b 后半，下一步）

- **谁能编程 DMA**：DMA 的 `S_AXI_LITE` 只挂 BD 互联 M02（0x44A1_0000），**只有
  软核可达** ⇒ SEQ 读引擎驱动 = **MicroBlaze 逐帧编程 DMA**（沿用 'D' 命令已走通的
  MM2S_SA/LENGTH 直写序列），RTL 侧只做 shim 拆包 + 回灌 frame_mem_if 读路径；
- **软核所需输入**：当前 SEQ 读请求/槽号 + 该槽帧长（桥 `len_tab` 经 Lite 寄存器引出），
  据此算 `SA/LEN`；
- **RTL 改动**：shim 接 DMA M_AXIS；shim 的 `rf_wr_en/rf_wr_data`、`rdesc_*` 接到
  frame_mem_if 读路径（与原桥 R_UNPACK 同一落点），加"读引擎 = 桥 / DMA"模式选择，
  避免桥读 FSM 与 shim 同时驱动同一落点；
- **验收**：SEQ 模式读回帧逐字节等于 PC 载荷（DMA 路径），并与桥路径对照；顺带加
  ILA 探 DMA 的 M_AXI AR/R 以**定位 50 的真实机制**。

## 三之十七、M-B/M8/M11 实测（2026-10-16 深夜·续）：busy_ms 时基定案 + 驻留静默机制两级收敛

> 本节是 §三之十六规范固化后的**第一批按 L 等级标注的测量**。工具：绿配置（v5-RTL `708f15a4` + ELF `c13a54f5`）与复现配置（`3aa600aa` + ELF `f8175c32`）交替烧录。

### M-B：busy_ms 真实时基 `[L3-板证实]`

- 方法：绿配置上跑 `'E'` 轮（stall 退出路径），测 E-START→E-DONE 墙钟 6.1s ÷ 估算 busy_ms 调用数。
- **实测 `busy_ms(1)` ≈ 0.15–0.38 ms**（0.15ms 为纯循环理论值，0.38ms 为摊入 rd_reg 总线往返的观测值）。
- 反汇编手工展开乘法链（0x8d4–0x914）：`n = ms × 3300`（×5→×25→×33 复合移位加）；循环体 4 指令 ≈45ns ⇒ 理论 0.148ms ✓ 与实测吻合。
- **订正 §三之十六的判定**：busy_ms 不是"错 25 倍慢"，是**错 ~6.6 倍快**（设计意图 1ms，实际 0.15ms——3300 轮应为 33000 轮）。§三之十六中"×25 慢"的推断本身是一个 L0 误判，特此留痕。
- 影响重估：所有 busy_ms 标定的超时**实际比设计短 6.6×**（不是长 25×）——'E' 轮 stall 判定实际 ~4s×(1/6.6)? 不成立：实测 E-DONE 总 6.1s 说明 stall 路径的总时长与 4000 轮×(rd_reg+busy_ms) 自洽，**超时行为量级正确**，仅绝对换算需按 0.15ms/次重标。

### M8/M11：驻留静默的机制收敛

**M8（挂点身份）`[L3-板证实]`**：复现配置静默时 `stop` 后读寄存器——`PC=0x91c`（busy_ms 循环体）、**`R15=0xa3c`（rd_reg 内的 busy_ms 调用点）**、`R5=1`（参数 ms=1）⇒ 软核正执行 `rd_reg→busy_ms(1)`，即主循环 `while(!urx_poll()){serve_dma_once();}` 的正常路径中。

**M11（栈上倒计时 n）`[L3-板证实]`**：三次 stop 采样读 `R19+4`（busy_ms 的局部 n）：`0xafe(2814) → 0x1ed(493) → 0x2df(735)`——**n 正常递减且跨调用**（第三次回升 = 新一次 busy_ms 已开始）⇒ **软核没有卡死在单个 busy_ms**，主循环健康运转、serve_dma_once 每圈正常进出。

**两级收敛后的剩余未知 `[L1-假说]`**：

## 三之十九、驻留静默根因定案与修复（2026-10-17 日场）：**坑 #39 打在 `urx_poll` 的单次读上**

### 1) 根因 `[L4]`（软核侧实测 + 修复复验闭环）

- `'U'` 探针（软核自己的总线时序，不经 JTAG）实测 M01 读形态：
  `U id:  00000017 50314231 50314231 50314231 50314231 50314231`（首读 `0x17` = 上一笔残余，其后 5 连读恒为正确 ID）；
  `U req: 50314231 00000000 …`（首读恒等于**前一地址**的值）。
  ⇒ **坑 #39 的真实形态 = "一笔滞后；同址连读第二笔即正确"**。
- 驻留服务的空闲环是 `while (!urx_poll()) { if (g_dma_mode) serve_dma_once(); }`，而 `serve_dma_once()` 第一句是 `rd_reg(+0x34)`，`rd_reg` 内含一次**哑写 0x2C**；`urx_poll()` 原本是**单次读** `UART_ST` ⇒ 每一笔都落在"紧跟写之后的第一笔读"位置 ⇒ `RX_VALID` 恒读成 0 ⇒ **软核永远收不到字节 ⇒ 串口静默**。与位流无关。

#### 2) 根因（[L4] 定案：代码级 + 板上直接观测 + 修复前后对照）

**2.1 代码级：退役改动落在两个桥共享的模块里，桥② 被连坐**

- 提交 `8afa168`（2026-10-16 18:37）在 `prj\project_11\rtl\axi4_master_bridge.v` 把 R_PRE 的引擎二选一：

```verilog
// 退役前（3f847e3）
end else if (dma_engine) begin   // DMA 读引擎：发 {slot,len}，等 shim frame_done
    dma_req_new <= 1'b1; ... rstate <= R_DRET;
end else begin                   // 桥硬件读引擎：R_AR→R_R→R_UNPACK→R_FIN
    r_slot<=p_eff; ... rstate <= R_AR;
end
// 8afa168：去掉 dma_engine 条件，无条件进 DMA 分支，并删除 R_AR/R_R/R_UNPACK/R_FIN
```

- 该模块由 `frame_mem_if` 内 `u_bridge` 例化，而 `HAS_DMA` 由顶层决定：桥① `u_mem`（`aurora_mem_bridge.v:772`，默认 `HAS_DMA=1`，有 DMA shim）与桥② `u_mem2`（`:917`，**`HAS_DMA=0`**，DMA 口恒 0：`:956`）。
- 桥②（`HAS_DMA=0`、无 shim）在退役后：① R_PRE 无条件进 **R_DRET**，而 `shim_frame_done` 在 `HAS_DMA=0` 分支**无驱动**（退役归档 `axi4_master_bridge_retired.v:547` 只声明 wire）⇒ 恒 0、R_DRET 无出口（无超时/看门狗，H6）⇒ 读 FSM **永久停泊**；② `gen_no_dma` 的 `rf_wr_en=brf_wr_en`，而 `brf_wr_en` 只在已删的 R_UNPACK 置位 ⇒ **读数据口无源**；③ 桥② 是泵B 唯一数据源（`aurora_mem_bridge.v:1194-1206`）⇒ 泵B 无输入 ⇒ 出向帧全部停在上线前。
- **结论**：退役的正确作用域是 `HAS_DMA=1` 实例；8afa168 用"无条件删分支"实现，等效于把作用域扩大到 `HAS_DMA=0` ⇒ 结构性误伤。

#### 9) 教训（写进坑账本：#55 共享模块退役作用域；#56 判据工具缺陷/失败纪律）

**① 旧 S2–S6 脚本两处失效**

`out\retire_s2_s6.ps1` 的 S4 跑 `manual_round.py COM5 1`（`'M'` 轮）后 S5 直接 ping。固件 `round_command()`（`sw\src_j3\main.c:340-382`）：轮末把 `R_ENGINE` 写回 0（`:375-379`）、`R_MODE` 停在 RND 且不恢复（`:358`，注释 `:380-381`）⇒ RND 下顶层不自动发读请求（`aurora_mem_bridge.v:322-327`）⇒ **S5 读侧零启动**。⇒ 判据：**任何"M/A/B 轮之后直接 ping"的对照都无效**（绿位流同样 0/N）；有效判据必须「上电 → `'d'`（确认 DMA）→ ping 中途不跑 M/A/B → 前后 `'U'` + NIC delta」。

**② 共享模块的"退役/删除"必须按实例作用域做**

删逻辑/状态机前先枚举**所有实例及其参数化差异**（本模块 2 实例：`HAS_DMA=1`/`0`）。只看顶层实例端口接线（"u_mem2 的 DMA 口恒 0、没碰它"）会漏掉**模块内部共享逻辑**——20:45 离线审计即此漏。正确写法 = 用 `HAS_DMA` 之类**结构常量**在模块内分支，并写明分支对哪个实例生效。

**③ 参数化守卫要选结构常量，不要选运行态位**

`dma_engine` 是 `'d'` 可翻转的运行态开关；用它守卫会让缺陷随 `'d'` 时隐时现，并破坏桥① 的 DMA-only 收口。

**④ 无超时的 `R_DRET` 是放大器，不是根因**

单笔 `frame_done` 丢失即永久停泊（H6）。排查先用**读退休计数**定性（桥② `mem2_rd_frm` 恒 0 一眼定位），再谈字节流，不要从最下游倒推。

**⑤ "文件存在 ≠ 证据有效"**

今天三份"看起来是证据"的无效产物：第一轮 ILA（engine 被翻回 bridge，CSV 已被覆盖）、第一次 `rdcap2` 抓取（probe 未解析）、`clean_engine1_ping_204258.log`（空格式串）。同名 CSV 被覆盖时用流程日志 + UART 时间戳界定轮次（`ilacap_*` 现为修复版轮，旧退役轮数据见 `ilacap_counters_summary.txt`）。

**⑥ 判据口径依赖环境态（静态邻居 → ARP 行为改变）**

静态邻居 ⇒ PC 不发 ARP ⇒ 板端学不到 PC MAC ⇒ 旧退役流 dst=广播、`ReceivedUnicast` 恒 0。⇒ 发射流判据掩 dst+IP-ID+csum+FCS；NIC 主判据用 `ReceivedBytes`。修复后 ping 通、板端 ARP 学到 PC MAC，dst 恢复单播（环境态恢复，不是逻辑变化）。

**⑦ 对照基线必须带"模式/序列前缀"**

同一绿位流：四档 PASS，而 `--dma` J3 FAIL；后者根因是**判据脚本**缺陷（§4.2）⇒ "绿 = 全好"与"脚本 = 中立"都不成立；判据写成「绿 + 桥模式 + 四档 = PASS」「绿 + `--dma` + 修复后 `j3_soft_verify` = PASS」。

**⑧ 判据工具自身也是被测件：先查脚本再查 RTL（[L4] 实证）**

`j3_soft_verify.py --dma` 的三次 `wr+255` 最终定位为脚本预热帧占槽（不是硬件）。⇒ 看到"判据前差 1 帧/差 1 槽"的 off-by-one，优先核对**脚本在判据前的副作用**（预热帧、哑写、状态查询、引擎翻转）。这也解释 §三之十九之补 §1 "DMA 三链 PASS" 与今日 FAIL 的"矛盾"：不是硬件退化，是脚本缺陷在不同模式下暴露不同。

**⑨ 失败纪律：`wr+255`/收帧停摆不得重试**

重试会级联更多假 FAIL，并可能把板卡留在"256 槽未读 + 读 FSM 泊 `R_DRET`"半楔死状态（需重烧）。正确处置 = 判「判据未取得 + 板卡需重烧」，**新烧录后重跑**；J3 前必须清槽（`'S'` + 只读检查 `wmwr==wmrd` 且 `req.bit25=0` 连续两拍）。

**⑩ 收口顺序（本次验证有效的顺序）**

位流身份（S2b 不发 `'d'` ping 必须 0）→ 引擎位双重确认（S3）→ 静默窗（S3b）→ 单帧（S4）→ ping×4（S5）→ `'U'` 分叉（S6）→ 桥级 ILA（S7）→ J3 四链（S8b）→ 发射流同构（S8c）→ 四档（S8d）。**每一步都先证"判据取得"再谈通过**（NOT_OBTAINED ≠ PASS）。
