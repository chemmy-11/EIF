### 1.3 两工程共享 RTL：prj12 是 prj13 的“前置门禁”而不是并行项

prj12 与 prj13 的以下模块**逐字节相同**：

| 模块 | SHA256 前缀 | 影响 |
|---|---|---|
| `axis_word_unpack.v` | `F49EA7002914…` | P2 的 Aurora RX 解包复用；若 unpack 少吐 64 B，P2 A→B 同样短 |
| `frame_mem_if.v` | `B9B701B1857B…` | P2 的 `u_mem2` 复用；若长度/提交逻辑丢 64 B，P2 同样中招 |
| `axis_word_pack.v` | `74AB46064A94…` | P2 的 mem2→RGMII pack 复用 |

P2 的 A→B 接收链：`Aurora RX → u_unpack → p2_relay 重加 14 B 头 → u_mem2（同一 frame_mem_if）→ pack → RGMII`。与 P1 只差中间插入 `p2_relay` ⇒ **−64 B 缺陷大概率被 P2 继承**。不做 B1D 定案直接上 P2，等于把同一 bug 在观测更少的 P2 上再追一遍。

### Q1：吞吐评估的“被测对象”和顺序

背景事实：
- J0 **线格式已冻结为 GPP2/v1**（`docs/refs/protocol_v2_GPP2.md`：52 B 头、JSON META、逐片 ACK、META ACK、8 MiB、1200 B datagram）；**未冻结**的是 API 语义、labels/session 细则、A 侧能力值。
- “用 B 组协议做 iperf 压测”要区分三种东西：
  1. **iperf/裸 UDP**：测 IP/UDP 管道能力（无 ARQ），回答“P2 管道能吃多少”；
  2. **GPP2 可靠 UDP**（B 组 `b2_reliable_udp.py` 等）：测协议在给定窗口/RTO 下的有效吞吐（含重传/ACK 开销）；
  3. **J0 冻结**：线格式已冻，剩下 API/能力值/默认参数——应由 1、2 的数据决定。
- iperf3 需要 TCP 控制连接（5201）；若 P2 只保证 UDP 透传，iperf3 TCP 会失败，需 iperf2 UDP 或自研 UDP；iperf 走 OS 栈，**需要管理员**配 IP/静态 ARP。

方案必须回答：
1. 下一轮吞吐评估的主被测对象（裸 UDP / iperf / GPP2 负载 / 组合）与**顺序**；各自能回答/不能回答什么。
2. 如何避免把**协议自身限制**（窗口 8、RTO 250 ms、逐片 ACK）误判成“管道上限”？归因方法是什么？
3. 哪些数据会改变协议参数/默认值/API 语义？哪些只进 A3 报告、不动协议？
4. “冻结”还剩哪些动作、分别在什么数据之后做？是否需要在 iperf 出数前保持 API 语义不冻？
5. 若 P2 双板尚不可用，是否接受先用 P1+B1 的 L0 冒烟给出**非正式上界**？如何标注、不能用于什么？
