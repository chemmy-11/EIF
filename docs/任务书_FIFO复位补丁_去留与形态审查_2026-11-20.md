## 0. 一句话

prj12 曾为修一个"闪断后写通路自锁"的死锁打了 B1 补丁（把 `frame_mem_if` 内 5 个异步 FIFO 的两侧复位做配对）。这个补丁**只是部分修复**，而 prj13 现在带着它仍然会在一次 link-down→up 之后不可用。负责人提出：**如果运营上本来就是"任何异常就拔纤 + 重启/重烧"，那这个补丁到底还要不要做？**

## 1. 负责人给定的运行前提（这是决策的边界条件，请当成硬输入）

> 「任一侧重烧本来就不是预期工况，只是实验中迭代才需要。其实可以重烧的时候我把光纤或重启板子，如果这样能解决就不用特意打补丁。」

即：
- **正常运行期**：不会重烧、不会拔纤、不会对端断电。
- **维护期**：需要重烧时，负责人可以同时拔光纤 / 重启板子。

## 2. 补丁是什么（RTL 事实）

### 2.1 缺陷本来的样子

`prj/project_13/rtl/frame_mem_if.v:98-104` 的端口注释原文：

```
// ★B1 (2026-11-07 dma-stall): ui 域 **FIFO 侧**复位, 必须与 user_rst_n 成对。
//   缺陷: 二者原本分接 ~aurora_rst / ui_rst_n, Aurora 闪断时只有一侧指针归零,
//         另一侧留在 Q -> 水位读成 8192-Q -> wr_hold 永久粘滞 -> 写通路自锁,
//         且只有 ui_rst_n(=MIG ui_clk_sync_rst, 仅 POR/按键/重配置)能清。
//   范围: 只驱动下面 5 个 async_fifo 的 ui 侧指针；桥/槽表仍用 ui_rst_n
//         (避免 AXI 读 burst 中途被断)。见 out/evidence_2026-11-07_dma_stall/。
input  wire         ui_link_rst_n,
```

### 2.2 补丁的作用点

- `frame_mem_if.v:195/201/207/213/219` 实例化 5 个 `async_fifo`；
- `:198/204/210`（`u_wr_bytes` / `u_wr_desc` / `u_rd_cmd` 的 **rd_rst_n**）与 `:214/220`（`u_rd_bytes` / `u_rd_desc` 的 **wr_rst_n**）全部改接 `ui_link_rst_n`；
- 顶层生成：`prj/project_13/rtl/aurora_mem_bridge.v:289-296`

```verilog
reg [3:0] arst_ui_pipe;
always @(posedge ui_clk) begin
    if (!ui_rst_n) arst_ui_pipe <= 4'hF;
    else           arst_ui_pipe <= {arst_ui_pipe[2:0], aurora_rst};
end
wire aurora_rst_ui = |arst_ui_pipe;
wire ui_link_rst_n = ui_rst_n & ~aurora_rst_ui;
```

- 两个实例都接（下述行号是 `.ui_link_rst_n(...)` 连接行本身，实例头在其上 1–2 行）：
  `u_mem`（`prj/project_13/rtl/aurora_mem_bridge.v:949`）、`u_mem2`（同文件 `:1106`）；
- `aurora_rst = ~sys_rst_n | ~link_ok`（`:247`）——**注意：它是电平信号，"链路不在"期间一直为 1**。

### 2.3 关键：补丁的作用域是**故意截断**的

注释已经说清：**只复位 5 个 FIFO 的 ui 侧指针；桥 / 槽表 / `ro_outstanding` 仍用 `ui_rst_n`**。

于是闪断之后：
- FIFO 指针两侧都清了 ⇒ **指针不再错位**（prj12 死锁被修掉的原因）；
- **但槽表与 `ro_outstanding` 没清** ⇒ FIFO 已经空了，设计仍认为"有 N 帧挂着"。

而读请求的触发条件是（`aurora_mem_bridge.v:399`）：

```verilog
mem_rd_req <= (mem_outstanding_sync != 9'd0) && !mem_rd_busy && !mem_rd_req;
```

`outstanding != 0` 但 `u_rd_cmd` 已空 ⇒ 读引擎拿不到描述符空转 ⇒ pack 永远收不到帧。

## 3. 实测事实（这是决策的主要证据）

### 3.1 prj12：补丁**有效**（有 A/B 对照）

同机型、同位流构建链、同工况（背靠背饱和流量 + 拔纤 10 s），唯一变量是位流：

| 位流 | `pfwd_wr` | `pk_frames` | `mem_wr_frm` | `mem_u_drop` | 判定 |
|---|---|---|---|---|---|
| 基线 `C856BA83`（**无**补丁） | 3 | **0** | 停在 6001 | **+3** | 死锁 |
| B1 `E9BE2B14`（**有**补丁） | 3 | **3** | 4457→4460 | 0 | 恢复 |

- 恢复阶梯（在死锁态实测）：`d` 翻转无效 → `rst -processor`+`dow` 无效 → **整板 BitElf 重烧有效（16 s）**。
- 结论：**补丁对 prj12 是有效修复**，不是安慰剂。

### 3.2 prj13 P2：补丁**没带来可用性**（同代码，不同行为）

prj13 的 RTL 与 prj12 **逐字相同地**带这个补丁（同样的 5 个 FIFO、同样的 pipeline），但实测：

| 时刻 | 操作 | A 侧实测 |
|---|---|---|
| 20:24 | 正常运行 | `pfwd_wr=12 / pk_frames=12` ✅ |
| 22:53 | 对侧重烧 → 链路闪断 | `pfwd_wr=3 / pk_frames=0`、串口 `wr=3 rd=0` ❌ |
| 23:08 | 重烧 A | `pfwd_wr=3 / pk_frames=3` ✅ 恢复 |
| 23:12 | **光纤断开**下重烧、再插回 | `ch_up=1 / aurora_rst=0` 但 **`pk_frames=0`** ❌ |

⇒ **一次 link-down→up 就让前向泵永久停摆，只有整板重配置能恢复**（与 §2.3 的槽表泄漏一致）。
⇒ 而且**任一侧重烧都会让对侧闪断 → 对侧卡死**，形成互拖循环。

### 3.3 一个更根本的事实：**闪断不可被检测**

`aurora_mem_bridge.v:1457-1467`：

```verilog
always @(posedge user_clk) begin
    if (aurora_rst) begin
        hard_err_cnt <= 16'd0; soft_err_cnt <= 16'd0; ch_up_evt_cnt <= 16'd0;
        ...
    end else begin
        ch_up_d <= channel_up;
        ...
        if (ch_up_d & ~channel_up) ch_up_evt_cnt <= ch_up_evt_cnt + 16'd1;
```

`aurora_rst = ~sys_rst_n | ~link_ok`。**链路一掉，`aurora_rst` 立刻把"发生过闪断"的证据清零**，而那个 `else` 分支的计数因此永远执行不到。

实测印证：今晚每一次闪断（`pfwd_wr` 被清零证明闪断确实发生），`dbg_ch_up_evt` 都读到 **0**。

⇒ 结论：**"闪断后必须重烧"这条运营规则，目前无法被执行**——只能靠人肉记得"我刚才拔过纤"。自发性闪断（电源波动、光模块抖动、对端重启）会让板子**安静地停摆**，且所有能报警的计数器都是 0。

## 4. 官方知识库依据（随任务书附上，供你直接引用）

### 4.1 PG057 · FIFO Generator v13.2 —— 异步 FIFO 的复位规则（**最关键**）

来源：https://docs.amd.com/v/u/en-US/pg057-fifo-generator

原文（Designing with the Core 章）：

> "For independent clock block and distributed RAM synchronous reset, because the reset pin (wr_rst/rd_rst) is synchronous to the respective clock domain, no additional synchronization logic is needed. However, it is recommended to follow these rules to avoid unexpected behavior:
> **If wr_rst is applied, then rd_rst must also be applied and vice versa**
> **No write or read operations should be performed until both clock domains are [out of] reset**"

> "The generated FIFO core will be initialized after reset to a known state"

> "**Continuous Clocks** — The FIFO Generator core is designed to work only with free-running write and read clocks. Xilinx does not recommend controlling the core by manipulating rd_clk and wr_clk. If this functionality is required to gate FIFO operation, we recommend using the write enable (wr_en) and read enable (rd_en) signals.
> Note: If the clock(s) is/are lost during the normal operation, use BUFGCE to make clock line flat to ensure that the FIFO Generator core is not operating on a perturbed clock. **It is highly recommended to apply reset once the clock(s) is/are stable.**"

**对本问题的意义**：
- 补丁让 `wr_rst`/`rd_rst` 同时被拉起，**方向是对的**；
- 但 AMD 要求"两侧都处于复位期间不得读写"。本补丁的**释放是不对称的**：`user_rst_n = ~aurora_rst` 立即释放，而 `ui_link_rst_n` 还要等 `arst_ui_pipe` 4 拍排空才释放 ⇒ **存在 user 侧已可写、ui 侧仍在复位的时间窗**。这可能是 prj13 行为与 prj12 不同的一个嫌疑点（待证）。
- "clock lost 时先让时钟稳定再复位" —— Aurora 的 `user_clk` 在链路掉线期间是否仍然自由运行，值得核实（若 `user_clk` 会在链路丢失时停摆，则 user 侧的复位释放时机不可控）。

### 4.2 AMD Answer 38023 —— 异步复位的最小脉宽与读写禁止

来源：https://adaptivesupport.amd.com/s/article/38023?language=en_US

> "There are two asynchronous reset behaviors… Full flags reset value of 1: FIFO requires a minimum asynchronous reset pulse of 1 write clock period… So **wr_en and rd_en cannot be asserted when reset is asserted in order to avoid unexpected behavior**."
> "Asynchronous reset behavior (Memory Type is Built-in FIFO) — Built-In FIFOs require an asynchronous reset pulse of at least 3 read and write clock cycles. **During reset, wr_en and rd_en cannot be asserted.**"

**对本问题的意义**：补丁释放不对称时，若 user 侧先恢复并立刻写（`wr_en` 有效），而 ui 侧仍在复位，就落在"reset 期间 assert wr_en"的禁区里。

### 4.3 AMD Answer 42571 —— 复位必须同步到读时钟

来源：https://adaptivesupport.amd.com/s/article/42571?language=en_US

> "signals that are internally generated within the built-in FIFO… **To avoid this issue, synchronize the Reset to the RDCLK** and ensure that the other reset requirements of the family are met… **The Reset must be synchronized to the RDCLK before being passed to the core.** In UltraScale/UltraScale+ MPSoC devices, there is a synchronizer for the reset to WRCLK, so this no longer applies."

**对本问题的意义**：`ui_link_rst_n` 虽然是用 `ui_clk` 打拍生成（等效于同步到读时钟域），但**它的释放沿是由 `aurora_rst`（user/eth 域的链路状态）跨域传过来的**，跨域本身带不确定性；这与 42571 描述的"复位跨域未同步"风险同类。

### 4.4 UG573 —— 独立时钟 FIFO 的同步语义

来源：https://docs.amd.com/r/en-US/ug573-ultrascale-memory-resources/Independent-Clock/Dual-Clock-FIFO

> "Due to the internal synchronization between the WRCLK domain and the RDCLK domain, certain transitions take an extended number of clock cycles… Only after the write operation has synchronized to the RDCLK domain is that write operation reflected in the status of the RDCLK outputs EMPTY and PROGEMPTY."

**对本问题的意义**：复位释放后的若干拍内，空/满标志仍是旧的/悲观值。上层若用 `wr_hold`/水位做流控，需容忍这段过渡期。

## 7. 提出方目前的倾向（**仅供参考，你有权推翻**）

供你判断时对照，不必被它带偏：

1. 倾向 **C**：补丁在 prj13 里没带来可用性（实测），但它把失败模式从"静默错位"变成"响亮停摆"，**不主张移除**；真正缺的是"闪断不可检测"。
