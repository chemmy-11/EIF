# M1 · prj12 + prj13 下一轮联合实施方案

machine=PC2；本机角色为物理板 B 执行者。本文件是供负责人审议的方案，不是板级执行记录。
本次依据 2026-11-17 任务书编制；附件中的执行步骤只转换为计划，不视为立即访问板卡或发布评论的授权。
本方案写在 pc2/，不就地修改只读的 prj/、docs/ 或根规范。

## 1. 结论摘要

**Q0：采用 prj12 一次性收尾，先诊断，后按证据修复，再验收冻结。**
B1D 是已就绪的最低成本诊断件；两工程共享三个模块的事实已核验，但“P2 继承 −64 B”仍是 `[L1-假设]`，不能预先指定改 unpack。
G0 的 +142/+78 是分诊门，不是 L4 根因定案；G1 需对照、补丁与修复复验闭环。prj12 不加新功能、不做长期并行线。[E1–E4]

**Q1：先裸 UDP/iperf2 管道能力，再同路径 GPP2 默认参数及单因素调参。**
GPP2/v1 的线格式、META/ACK 和 labels 约定已经冻结，不重新选协议；吞吐数据回填 A 侧能力及实现默认参数，不擅改 wire。
API 命名可以先审，完成/超时/取消/重启语义要结合实现与故障测试，不以 iperf 出数决定全部 API。[E7–E9]

**Q2：推荐“单板档 1 → 档 2 → 双板”，同时在另一台主机离线构建板 B。**
正式 G4 必须在 G0–G3 交接后开展；当前 PC2 正在跑的 A 参数修复对照构建仅为预研，不得越过 prj12 门禁。
下一轮正式 P2 A/B 两版均合入经验证的必要补丁及完整计数可观测性，再各自构建；不把现有无 DROP 探针对照版冒充 V4 版。[E5–E6、L1]

**统一路线**：`G0 B1D诊断 → G1修复/排除共享风险并重建 → G2双向M1-A+#23 → G3冻结prj12 → G4 P2单板两档 → G5 P2双板V4 → G6裸UDP→GPP2→能力/API签收`。
旧文档 V3 是反向 mem2 闪断诊断，前移到 G2/#23；G5 引用它的证据，不重新制造已知死锁，也不把“P2 B→A正常转发”误叫旧 V3。[E5:234–236]

- **构建预算**：B1D 0 次；prj12 正式修复候选 1 次；P2 A/B 各 1 次，共 **3 次完整构建**，假设每个阶段一次收敛。共享缺陷被排除仍需记录 G1 出口；可复用逐字节相同且满足观测条件的候选，实际次数据此减记。当前 A 对照预研另计 1 次，不算正式 V4 交付。每个时序失败候选另留一次实现重跑，绝不预填成功。
- **板窗口预算**：W0 B1D **0.5–1 h**；W1 M1-A/#23 **1–2 h**；W2 P2 单板 **45–60 min**（含切换）；W3 双板 **1–1.5 h**；W4 A3 **4.5–7 h**（初筛、扩展、故障/语义分2–3窗）。总计约 **7.75–12.5 h**，不含返修、交接和等待构建。
- **今天下午优先 W0**。若 G0 未取得有效分诊证据，下午停在证据整理，不硬排全部 P2/A3；诊断修复保留 **0.5–1 天计划余量**，不能承诺一小时改完。

### 3.1 G0：B1D 诊断轮（下午第一优先）

1. PC1/PC2各持有同一 B1D bit、LTX、BA3C0220 ELF；以§6完整hash核验。配置中 boards.B 的 cable/COM/NIC 必须现场回填，旧序列号/COM不作当前身份。
2. 本机工具串行、负责人发窗口；两板逐块烧 bit+ELF，核对成功标记、最后一条 now=DMA、链路健康，再做3帧门；不抢对端正在抓取的窗口。
3. 独立run_id、静默背景，每方向发1帧len100，抓发送/接收pcap及计数前后快照。记录up_bytes/up_stall/pfwd_drop/prev_drop、up_frames及mem2计数；16位计数做模65536差分，并排除期间复位/多余帧。
4. 同日补len1200/1472检查长度依赖；反向B→A为方向对照。若要归因B1补丁，必须另做基线C856BA83/B1 E9BE2B14的同拓扑对照，不能只靠B1D单侧。

| 观测 | 允许结论/下一步 | 禁止结论 |
|---|---|---|
| up_bytes +142，输入也确认142B | 计数点已吐预期字节；优先核对len_tab/wr_commit_len/mem2/pack边界与长度 | “唯一根因已是mem2” |
| +78，输入确认142B | 到该计数点已有缺口；追TX keep/last、实际输入和unpack字节/计量 | “unpack根因已定” |
| stall/drop/overflow有增量 | 按计数对应语义检查丢弃/背压，保留同run前后证据 | 不区分原因就写硬件损坏 |
| 其他增量、served=0、复位/背景流干扰 | 判据未取得；查流量与计时，最多重做两次受控run后归档阻塞 | 把恒零当通过，硬塞+142/+78分支 |

G0出口是**可复现、边界清楚的诊断记录**；尚未修复时根因标签最高按已有证据写L1/L2，不以该门名称声称L4。

### 4.1 工具及测量口径

- 主工具选**可明确限速/序号/字节统计的OS UDP测试**；iperf2 UDP可作对照。PC2当前PATH无iperf/iperf3，先登记可信安装源、版本、exe hash、--help和PC直连结果，不在本次方案编制中安装。
- iperf3 UDP也先建TCP控制连接（默认5201）；只有同FPGA路径TCP控制已证明可用才作为测试工具。若控制失败，记工具前置失败，不能直接判UDP数据面FAIL。[E13]
- RAW L2注入只用于无管理员时的字节诊断，不代替OS栈/ARP/iperf正式能力。CPU发包达不到报价时，以**实测送入**速率为自变量，不拿命令-b数值当实际输入。
- 统一单位：UDP payload L含全部GPP2 datagram；GPP2 header52B，Tensor片≤1148B，UDP payload≤1200B，IP≤1228B。GPP2 Tensor goodput只计唯一有效Tensor字节，剔除META/ACK/重传；另报UDP/IP/wire开销。[E7:19–42]
- 由prj11外推的19.2–24.576Mbps仅作选扫描区间的L1假设。W×1148×8/实测ACK RTT是窗口约束候选，不能把250ms RTO当正常RTT；真实goodput还受管道、反向ACK、CPU限制。

### 4.2 哪个数据决定哪个参数

| 数据/对照 | 决定项 | 不得据此修改 |
|---|---|---|
| 无ARQ包长扫+完整IP校验 | A能力max_udp_payload_bytes（单位UDP payload） | 冻结GPP2的1200B上限，1472管道通过不代表协议可扩大 |
| 方向/长度/突发的0丢最高档、丢包拐点、3轮最差值 | max_safe_rate_mbps，附方向、层级及条件 | 不能把loss≤0.1%称零丢；不从单点推出全尺寸能力 |
| ACK RTT、在途峰值、retx、队列DROP，固定RTO单改W | 默认W/max_inflight_segments | 不以256槽数直接定可用窗口，不改逐片ACK语义 |
| RTT尾部、OS停顿、重启恢复，固定W单改RTO | RTO、retry/deadline配置建议 | 不能用RTO代RTT推正常上限 |
| DROP与背压实测 | buffer_full_behavior/报告能力 | 没探针就TO_MEASURE，不虚构“自动重试/无损” |
| B代码审查+timeout/cancel/reset/labels端到端 | API完成与错误语义签收 | 全ACK≠应用已消费；iperf不能决定API命名/取消语义 |

**归因方法**：同一镜像/方向/尺寸分别测PC直连、P2裸UDP、GPP2；每轮只改一个W或RTO，记录CPU和ACK反向负载。
裸UDP也掉且FPGA drop随输入上升才收敛数据面候选；裸UDP有余量而GPP2随W/RTT变化只支持协议/主机候选。
任何根因结论遵循L0–L4，不能“排除窗口→证明FPGA”。瓶颈明确前不引入描述符批量/退DMA等新架构。

### 4.3 冻结动作与P1冒烟
